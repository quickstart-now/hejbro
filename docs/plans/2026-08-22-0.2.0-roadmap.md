# hejbro — Road to 0.2.0 (Phase 10)

Date: 2026-08-22
Phase issue **#282**. **Release policy (D83, owner 2026-08-22):** every
feature in this phase ships on the **0.1.x line as a `patch`** release
(0.1.2, 0.1.3, …) as it lands; **0.2.0 is cut by the owner as a stability
milestone** once the shipped set has been dogfooded — 0.1.0 was not the
stable release the owner intended (0.1.1 was), and the next `minor` must
not repeat that. So "0.2.0" in this document names the destination, never
the release a feature arrives in.
Prerequisite reading: `docs/specs/2026-08-19-hejbro-design.md` (the design
spec and decision log — still the single source of truth for decisions;
0.2.0 adds rows to it, it does not fork it) and `.specify/memory/constitution.md`.
The 0.1.x line (Phases 0–9) is `docs/plans/2026-08-19-roadmap.md`; that
document is closed and is not extended.

This roadmap is deliberately thin. **From Phase 10 the plan of record for a
feature is its Spec Kit directory** (`specs/NNN-<feature>/{spec,plan,tasks}.md`),
not a section here. This file holds only what is release-wide: the process
decision, the scope candidates, the work list, and the frontier.

## Process (D82)

Each Phase 10 feature runs **GitHub Spec Kit** (v1.0.x) for the *what* and
the superpowers cycle for the *how*:

```
/speckit-specify → /speckit-clarify → /speckit-plan → /speckit-tasks
      (specs/NNN-<feature>/)                 │
                                             ▼
   superpowers: TDD · subagent-driven development · review · worktree · PR
                                             │
           /speckit-analyze (before code) · /speckit-converge (before close)
```

- Owner decision 2026-08-22: **pilot first** (option C). The scaffold +
  constitution + one feature go end-to-end; the owner then decides whether
  every remaining feature follows. The verdict is recorded below.
- Verified on the scaffold: `specify init --here --integration claude`
  writes only `.specify/**` and `.claude/skills/speckit-*/SKILL.md`; no
  `.claude/settings.json` hooks, no tracked file touched. The `git` and
  `agent-context` extensions stay **off** — worktrees, `upstream` branches,
  issue-first and `CLAUDE.md` = `@AGENTS.md` are unchanged; Spec Kit tracks
  the active feature via `.specify/feature.json`, not the branch.
- `/speckit-implement` and `/speckit-taskstoissues` are **not used**:
  execution belongs to the repository's agent team; issues go through the
  repository's issue workflow (type, label, assignee, parent, board).
- Templates are customized only under `.specify/templates/overrides/`
  (tests mandatory with the layer named, the Constitution Check table, a
  "Decision-log impact" section). Core templates are never edited.
- Constitution v1.0.0 (`.specify/memory/constitution.md`): six principles
  derived from `AGENTS.md` and the decision log — core purity; the provider
  interface is the product; deterministic, reviewable, non-destructive
  output; test-first, three layers, CRAP ≤ 5; decisions logged and
  owner-approved; spec before code, one feature at a time.

## Scope candidates

Source: the 2026-08-22 gap analysis against Drizzle (pg-core 0.45.2 /
drizzle-kit 1.0.0-rc.4) and Prisma (7.9.1 GA / 8.0 RC), checked against
hejbro `dev@6061faa`. **Nothing below is in scope until it has a sub-issue
and a `specs/NNN-*/` directory**; the list is the menu `/speckit-specify`
picks from, one feature at a time, with the owner.

Where hejbro already leads (neither competitor does it): functions and
triggers compiled from TypeScript, grants, RLS as a typed builder, storage
buckets, flag-driven renames, drop protection, chain `verify` / `history` /
`restore`. Prisma 8 (RC) narrows the RLS lead; the function/trigger
compiler stays unique.

| Area | Candidate | Competitor reference |
|------|-----------|----------------------|
| Indexes | `using` method (btree/hash/gin/gist/spgist/brin/hnsw/ivfflat), expression indexes, operator classes; later `include`, `concurrently`, `with (…)` | Drizzle all; Prisma `type:`/`ops:`, expressions in 8 |
| Columns | pgvector / PostGIS types, `customType` escape hatch, `bit`/`money`/`xml`/`tsvector`/`macaddr8`/`citext`, time precision | Drizzle pg-core + `customType`; Prisma `@db.*` / `Unsupported` |

## Pilot verdict (#284, index completeness)

Recorded 2026-08-23 by the session that ran the pilot end-to-end (what
layer 2026-08-22, how layer 2026-08-22/23 with the hejbro team: 22 commits,
three stories, one `patch` changeset → 0.1.2). This is the assessment the
owner asked for; the owner's decision on the process for the rest of the
phase is recorded at the end of this section.

**Ceremony cost.** The what layer (spec + 3 clarifications, plan with
Constitution Check, research R1–R14, data-model, three contracts,
quickstart, tasks T001–T067 — ~1,000 lines) took one session, about what a
`brainstorming` → `writing-plans` pass took in Phases 5–9 for a feature of
this size. The how layer took ~2.5 h wall-clock with the team. The
artifacts paid back twice: docs, changeset and the D84–D86 rows could be
written on day 0 in parallel (their wording was already fixed), and the
reviewers had contracts (`contracts/errors.md`, `contracts/sql.md`) to
gate each story against instead of re-deriving intent.

**What the ceremony caught and missed.** Clarify turned three open
questions into owner decisions before any code (D84 format policy, D85
closed method list, D86 explicit names) — that is the part that worked
best. `/speckit-analyze` checks artifacts against each other, not against
the codebase or Postgres, so three defects in the plan of record surfaced
only during implementation: (1) `contracts/sql.md` rendered expression
columns without their own parentheses, contradicting research R9 and the
data-model grammar — operator expressions (`->>`, `||`) would have been a
Postgres syntax error; a reviewer caught it by applying generated SQL to a
live `postgres:17` (F7, fixed: always wrap); (2) `contracts/sql.md` step-2
and SC-005 expected a `--rename` of a column inside an index expression to
drop + create the index, contrary to D32 rule A (retarget the node) and to
Postgres itself (indexes reference attnums; no DDL) — fixed in the spec,
recorded under Clarifications "(implementation)"; (3) the golden harness
could not express a `--rename` step at all (minimal extension, one
`test(core)` commit). Smaller: tasks T007 described the golden snapshot
file wrongly (TDD caught it), and the Foundational type widening broke
three out-of-scope files at compile time (the compiler caught it — tasks
were written without compiling the type change). Net: Spec Kit improved
the *what*; its weak spot is contracts written without running anything.

**Override quality.** The spec override's "Decision-log impact" section
produced D84–D86 verbatim; the plan override's six-row Constitution Check
was meaningful (all PASS, re-checked after design); the tasks override's
mandatory test layer per task held. Gap: nothing in the templates asks for
a contract to be *exercised* before `/speckit-tasks`.

**What to change (recommendation).** Keep Spec Kit for the remaining
Phase 10 features with four adjustments: (a) a "contracts proven" step —
every SQL contract line is applied to a local Postgres (or recorded through
the golden harness) before `/speckit-tasks`; (b) when a task's body turns
out wrong, correct the body in place rather than appending a note (T034
still reads "drop + create" with a correction appended); (c) in the shared
worktree, commit with explicit pathspecs (two stray-staging incidents);
(d) two follow-up issues filed from the pilot — #287: `pnpm check-types` can be
falsely green (`@hejbro/supabase` type-checks against a stale core `dist`
— turbo `check-types` does not depend on `^build`), and
#288: `scripts/check-next-marker.mjs` exempts any message containing the string
"internal hejbro bug".
