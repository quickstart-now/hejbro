# hejbro — Implementation Roadmap

Date: 2026-08-19
Prerequisite reading: `/docs/specs/2026-08-19-hejbro-design.md` (the spec).

This roadmap decomposes the approved v1 scope into phases. **Each phase is its
own cycle**: brainstorm remaining unknowns if any → write a detailed
implementation plan (superpowers `writing-plans`) → implement with TDD →
review → PR. Do not start a phase by writing code.

Phases are ordered by dependency, not importance. Phase boundaries are also
good PR boundaries (one phase may still span several PRs).

## Phase 0 — Repo infrastructure ✅ (done at scaffold time)

Monorepo (pnpm + turbo), Biome, commitlint + husky, package skeletons
(`@hejbro/core`, `hejbro`, `@hejbro/supabase`, `@hejbro/skills`), MIT license,
spec + this roadmap. Remaining infra (CI workflow, vitest, build tooling
decision — tsup vs tsc) lands in Phase 1 when there is code to run.

## Phase 1 — Core object model + snapshot + diff for structural kinds

The "object kind" plugin interface (§4.1 of the spec) and its first
consumers: **schemas, tables/columns, enums, indexes, FKs**.

- Declaration model + normalized snapshot JSON format (versioned from day 1)
- Diff engine over kinds; `alter table` emission; rename detection question
  deferred to CLI phase (emit both candidates behind an explicit choice)
- Golden-file test harness (this phase sets the testing pattern)
- Add vitest + CI (`pnpm check`, `check-types`, `test`)
- Acceptance: declare the dd.land `posts` table family in a test, generate
  SQL from empty → full and between edits; golden files prove determinism

## Phase 2 — Expression & query builder foundation

Shared expression AST used by *everything downstream*: column defaults,
RLS `using`/`with check` expressions, view bodies, function bodies.

- Typed expression nodes (`eq`, `isNull`, `now()`, operators, literals…)
- Query builders: `select`/`insert`/`update`/`delete` with `where`,
  `returning` — enough to express real RLS policies and function bodies,
  not a full ORM
- SQL emission with correct quoting/escaping (security-sensitive: this is
  where injection-by-construction is prevented)
- Acceptance: golden files for a representative expression corpus

## Phase 3 — Function/trigger builder DSL + plpgsql compiler

The novelty. Builder execution tracing per spec §5.2/§6.

- `defineFunction` / `defineTrigger`; `ctx.row`, `ctx.if`, `ctx.return`,
  `ctx.raise`, variable declaration; recording proxies for row/column refs
- **Double-execution determinism guard** (hard error on differing trees)
- plpgsql emitter; signature-change detection → drop+create vs replace
- Start with the minimal control-flow set that ports
  `quickstart-labs/infra/dd-land-supabase/sql/comments-single-depth.ts`
  (the canonical motivating example: `if` + `raise` + row select). Loops
  (`ctx.forEach`) may land later in the phase
- Acceptance: the comments-single-depth trigger ports 1:1 and the emitted
  SQL is semantically equivalent to the hand-written original

## Phase 4 — RLS, views, grants kinds

- `rls.enabled` + policy declarations (using Phase 2 expressions);
  drop+create diff strategy
- `defineView` (create or replace; drop+create on column removal)
- `grant()` declarations; snapshot-delta → `grant`/`revoke` emission
- Acceptance: dd.land's `sql/grants.ts` equivalent expressed declaratively

## Phase 5 — CLI (`hejbro init` / `hejbro generate`)

- `hejbro.config.ts` (entry files, migrations dir, snapshot path)
- TS declaration loading (decide: jiti/tsx-style loader — needs a small
  research spike; this is the one place core purity meets the filesystem)
- Migration file emission with the banner comment format (spec §6.6)
- Interactive rename confirmation (table/column renames)
- Snapshot consistency check command for CI (declarations ↔ snapshot ↔
  migrations agree)
- Acceptance: `examples/` project generates end-to-end from the CLI

## Phase 6 — Supabase preset (`@hejbro/supabase`)

Built strictly on the provider interface — this phase is also the interface's
first real test (spec §4.1: if it needs a core special case, fix core).

- Role presets (`anon`, `authenticated`, `service_role`)
- `auth.uid()` typed helper
- Storage bucket object kind
- Reserved-schema protection (`auth`, `storage`, `realtime`)
- "Exposed table without RLS" warning
- Acceptance: dd.land example uses the preset; a second toy preset stub
  (e.g. `examples/preset-smoke`) proves the interface is generic

## Phase 7 — Real-PG round-trip CI + examples + skills

- Docker Postgres CI job: apply generated migrations → `pg_dump` → compare
- `examples/dd-land`: full port of the real dd.land schema
- `@hejbro/skills`: agent skill teaching the DSL, pitfalls (no real JS
  control flow), generate workflow
- README with positioning (spec §11), docs pass
- Acceptance: green round-trip CI on the dd.land example

## Phase 8 — Release readiness (owner-gated)

- Publish to the owner-held `@hejbro` npm scope under owner approval
  (OWNER ACTION); set `repository` fields and npm provenance to link back
  to `quickstart-now/hejbro`
- Versioning/changesets decision, CONTRIBUTING.md
- Announcement content (the AI-native build story is part of the launch)

## Deferred (explicitly out of v1 — do not build without owner approval)

- Migration apply command; live-DB drift check (`hejbro check`)
- Hybrid authoring (real TS arrows for single-expression SQL functions)
- Client type generation; Neon / Nile presets
- ESLint plugin against real-JS control flow (v1.x, after Phase 3 knows the
  exact failure modes)
