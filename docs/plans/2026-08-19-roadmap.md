# hejbro — Implementation Roadmap

Date: 2026-08-19
Prerequisite reading: `/docs/specs/2026-08-19-hejbro-design.md` (the spec).

This roadmap decomposes the approved v1 scope into phases. **Each phase is its
own cycle**: brainstorm remaining unknowns if any → write a detailed
implementation plan (superpowers `writing-plans`) → implement with TDD →
review → PR. Do not start a phase by writing code.

Phases are ordered by dependency, not importance. Phase boundaries are also
good PR boundaries (one phase may still span several PRs).

## Phase 0 — Repo infrastructure ✅ (done at scaffold time)

Monorepo (pnpm + turbo), Biome, commitlint + husky, package skeletons
(`@hejbro/core`, `hejbro`, `@hejbro/supabase`, `@hejbro/skills`), MIT license,
spec + this roadmap. Remaining infra (CI workflow, vitest, build tooling
decision — tsup vs tsc) lands in Phase 1 when there is code to run.

## Phase 2 — Expression & query builder foundation ✅

Landed: the typed expression AST (`nodeKind`-tagged union covering
literals, comparisons, logical/`in`/`between`, function calls, `sql`
templates, `sql.raw`, and `exists`) with injection-safe rendering
(`renderExpr`) and correlated-subquery scope validation; the operator
library (`eq`/`ne`/`gt`.../`inArray`/`between`/`and`/`or`/`not`/`now()`/
`genRandomUuid()`/`coalesce()`); the drizzle-style `table()` surface with
top-level typed `ColumnRef`s and symbol-hidden metadata (D15); the
`select`/`insert`/`update`/`deleteFrom` type-state query builders with
`where`/`returning`/`onConflict`/`orderBy`/`limit`; expression-based column
defaults replacing `ColumnDefault`, with the snapshot format bumped to v2
to store defaults as rendered SQL (D16); and a golden expression corpus
(`packages/core/test/expr/corpus.expected.txt`) exercising every operator,
injection-string literals, the `sql` template, the dd.land RLS shapes
(using/with-check, correlated `exists`, `exists` + inner join), and the
spec §5.2 function-body query shapes. See issue #3 for the tracking issue
and PR history.

Shared expression AST used by *everything downstream*: column defaults,
RLS `using`/`with check` expressions, view bodies, function bodies.

- Typed expression nodes (`eq`, `isNull`, `now()`, operators, literals…)
- Query builders: `select`/`insert`/`update`/`delete` with `where`,
  `returning` — enough to express real RLS policies and function bodies,
  not a full ORM
- SQL emission with correct quoting/escaping (security-sensitive: this is
  where injection-by-construction is prevented)
- Acceptance: golden files for a representative expression corpus
- Brainstorm resolved (2026-08-19, owner-approved): drizzle-style table
  objects with symbol-hidden metadata (D15); `ColumnDefault` fully replaced
  by the expression AST, snapshot v1 → v2 (D16); phantom typing by Postgres
  type family (D17); `sql` template always quotes interpolations, raw text
  only via `sql.raw()` (D18); expanded standard-clause scope — `order by`,
  `limit`, `on conflict`, `inArray` — and `with check`-shaped expressions in
  the golden corpus (D19). AST is a tagged union with `nodeKind` +
  `assertNever`; literal auto-lift covers string/number/boolean/null/Date

  `docs/plans/2026-08-19-phase2-implementation.md`

## Phase 3 — Function/trigger builder DSL + plpgsql compiler ✅

The novelty. Builder execution tracing per spec §5.2/§6.

Landed: a `plpgsqlRef` expression node (unquoted plpgsql-local references —
`new`/`old` fields, function args, locals — under the dual quoting policy)
and `renderSelectInto`, extending the Phase 2 expression/query layer without
touching its invariants; `defineFunction`/`defineTrigger` with a recording
`BodyContext` (`ctx.row`/`ctx.rowOrNull`/`ctx.if`(`.elseIf`/`.else`)/
`ctx.raise`/`ctx.return`) that declares one scalar local per projected
column (`${rowName}_${snake(key)}`, auto-counted when unnamed) and builds a
JSON-safe `FunctionBody` tree; a double-execution determinism guard — the
body callback runs twice at declaration time and a structural (`stableJson`)
mismatch between the two recorded trees is a hard `nondeterministic-body`
error — plus best-effort `declaredAt` capture (`captureDeclarationSite`,
pure stack parsing, no I/O) threaded through every declaration- and
recording-time error; a deterministic plpgsql emitter (`renderFunctionSql`/
`renderTriggerSql`) and the `function`/`trigger` object kinds registered in
the default registry (functions `create or replace` on an identical
structured signature, else a `drop function` + `create or replace function`
statement pair; triggers always recreate via an idempotent
`drop trigger if exists` + `create trigger` statement pair — both recreate
paths render from a **single `alter` `KindChange`**, not two separate
changes, so the diff engine's global create-before-drop ordering can't
split the pair; a `defineTrigger` input expands to
`[functionDeclaration, triggerDeclaration]` in `generateMigration`); and the
`comments-single-depth` golden acceptance case, a 1:1 port of dd.land's
hand-written trigger, manually verified semantically equivalent to the
original SQL. The acceptance golden's human review caught a real
engine-level bug this way (#55, fixed in PR #56): a same-identity recreate
represented as two separate `KindChange`s let the diff engine hoist the
create ahead of the drop, so the recorded migration dropped the trigger it
had just created — no prior test exercised a recreate through the full
`generateMigration` pipeline. See issue #4 for the tracking issue and PRs
#51–#58 for the implementer/reviewer cycle.

- `defineFunction` / `defineTrigger`; `ctx.row`, `ctx.if`, `ctx.return`,
  `ctx.raise`, `ctx.forEach`, variable declaration; recording proxies for
  row/column refs
- **Double-execution determinism guard** (hard error on differing trees)
- plpgsql emitter; signature-change detection → drop+create vs replace
- Ported `quickstart-labs/infra/dd-land-supabase/sql/comments-single-depth.ts`
  (the canonical motivating example: `if` + `raise` + row select). Loops
  (`ctx.forEach`) landed in-phase via PR #58 — decision A9 originally
  deferred them to a follow-up sub-issue (#50), which the owner then
  approved for in-phase landing once the rest of Phase 3 was done
- Acceptance: the comments-single-depth trigger ports 1:1 and the emitted
  SQL is semantically equivalent to the hand-written original (manually
  reviewed against the source migration)
- Brainstorm resolved (2026-08-19, owner-approved via main): `plpgsqlRef`
  node + dual quoting policy (A1/A3); scalar-per-column row locals over a
  `record` variable, strictness in the method name (A2); structural
  double-run determinism guard, declaration-site best-effort capture (A4,
  A8); function `create or replace` only on identical structured signature,
  else drop+create (A5); trigger always-recreate (A6); `ctx.raise`/
  `ctx.return`/`ctx.if` shape fixed for this phase (A10); `ctx.forEach`
  originally deferred (A9) then approved for in-phase landing (#50, PR #58)
  — its loop variable is a single `record` local, unlike `ctx.row`'s
  scalar-per-column strategy, since a `for … in` variable is reassigned
  fresh every iteration; function snapshot stores rendered `bodySql`
  alongside
  `bodyHash` since `ObjectKind.emit` renders from snapshot nodes only (A11,
  escalated to and approved by the owner mid-phase). Implementation plan:
  `docs/plans/2026-08-19-phase3-implementation.md`. Decision log entries
  D20–D24 (spec §3) record the phase's brainstorm outcomes in full.

## Phase 4 — RLS, views, grants kinds ✅

Security and read surface next to tables: policies, views, grants (spec
§5.4/§6.5).

Landed: two new declaration surfaces and four new object kinds, all built
on the Phase 1–3 `ObjectKind` contract without touching `tableKind`'s
snapshot shape (`HEJBRO_SNAPSHOT_VERSION` stays 2). `rls.policy(name)` is
a type-state builder chain — `for()` exposes only the clauses each
Postgres command allows (select/delete → `using`, insert → `withCheck`,
update/all → both, `.to()` mandatory) — and `TableExtras.rls` binds an
`RlsInput` to its owning table via `bindRls`, validating duplicate policy
names, illegal clause/command combinations, and top-level foreign-column
references (a correlated `exists()` is exempt — `collectColumnRefs`
deliberately doesn't descend into it). The `rls` kind (identity
`<schema>.<table>`) emits enable/force/disable; the `policy` kind
(identity `<schema>.<table>.<name>`) has no `alter policy` in Postgres, so
any change recreates via a **single** `alter` `KindChange` whose `emit`
orders drop before create (D23/#55 precedent, first applied outside
triggers/functions here). `defineView` copies an already-validated
`select()` chain's query node in as-is; the `view` kind derives its
column list from the query's projection and applies the **prefix rule**
(D27) — a previous column list that's a prefix of the next can
`create or replace view` in place, anything else (removal, reorder,
rename) recreates via the same single-`alter` pattern. `grant()` is a
type-state chain (`.usage` / `.tables(...)` / `.defaultPrivileges.tables(
...)`, each ending `.to(...roles)`) that fans out into one
`GrantDeclaration` per role (D28); the `grant` kind's identity is
`(schema, grantKind, role)`, so duplicate declarations fall out of
`buildSnapshot`'s existing `duplicate-identity` check with no bespoke
code, and `diff` is a privilege-set delta whose `emit` **recomputes** the
added/removed privileges from the snapshots rather than reading banner
notes — a review fix first applied to `viewKind.emit` (PR #71) and then
built into `grantKind` from the start (PR #72), establishing notes as
strictly display-only across every kind that recreates or deltas.

- `rls.enabled` + policy declarations (using Phase 2 expressions);
  drop+create diff strategy
- `defineView` (create or replace; drop+create on column removal)
- `grant()` declarations; snapshot-delta → `grant`/`revoke` emission
- Acceptance: `ddland-security` golden case — the dd.land `sql/grants.ts`
  corpus (1:1 port; its one `to anon, service_role` statement fans out to
  two per-role `grant usage` statements, semantically equivalent) plus a
  representative RLS slice ported from the **legacy** dd.land migrations
  (A6: current production dd.land is grants-only, so legacy is the only
  real RLS source available for the port) — `posts_read_published`,
  `post_translations_read_published`, `comments_read_visible` — plus one
  insert/`with check` policy shaped after a planner-supabase migration but
  expressed with core operators only (no `auth.jwt()`, Supabase-preset
  territory — Phase 6, #66). Manually verified clause-by-clause equivalent
  to the source SQL, the same review discipline that caught #55 in Phase
  3.
- Brainstorm resolved (2026-08-19, owner-approved): RLS as two additive
  object kinds rather than embedding into the table snapshot (D25); the
  policy type-state chain and mandatory `.to()` (D26); the view prefix
  rule (D27); grant identity and per-role fan-out (D28). Implementation
  plan: `docs/plans/2026-08-19-phase4-implementation.md`. Decision log
  entries D25–D28 (spec's decision log) record the phase's brainstorm
  outcomes in full. Landed across four PRs against sub-issues of #5: PR
  #70 (#62, rls/policy kinds), PR #71 (#63, view kind), PR #72 (#64, grant
  kind), and this acceptance/close-out work (#65). Typed roles,
  `auth.uid()`/`auth.jwt()` helpers, and RLS-related warnings are
  Supabase-preset work tracked as a Phase 6 follow-up (#66).

## Phase 5 — CLI (`hejbro init` / `hejbro generate` / `hejbro verify`) ✅

The pure Phase 1–4 core meets the filesystem and the clock for the first
time — `packages/cli` (the `hejbro` package) is the *only* place either
happens; `@hejbro/core` gained one new pure engine (`planRenames`,
`checkChain`) and stayed dependency-free throughout.

Landed: `hejbro.config.ts` loads through **jiti** (D29) — the same path
declaration entries use, exercising the `hejbro` package's own
self-import cycle (`import { defineConfig } from "hejbro"` from inside a
file jiti loads) — and is validated by a `defineConfig()` + zod schema
whose issues are re-wrapped into spec §7 diagnostic grammar; zod's own
error text never reaches the user (D30). Table/column/index/FK names
are validated against `^[a-z][a-z0-9_]*$` at declaration time (D36),
the strictness the `--rename`/`--confirm-drop` flag grammar's `.`/`=`
separators require. `hejbro generate` diffs the rebuilt-from-
declarations snapshot against the checked-in one, resolves any
same-table/-schema drop+add ambiguity via core's new `planRenames`
(rule A: type-agnostic, batch-collected, residual-set-aware so
partially-resolved reruns narrow correctly) against repeatable
`--rename`/`--confirm-drop` flags (D32) — every ambiguity renders as
the owner-approved rich terminal diagnostic (identity, body, and
concrete rerun-command suggestions built from `planRenames`'
*structured* residual data, not a re-parse of its flat message text) —
and, on success, writes the migration with the existing banner format
(spec §6.6) plus two new `parent-snapshot:`/`snapshot:` sha256 lines
(D33) that chain migrations together. `hejbro verify` reconstructs that
chain purely from the checked-out files (`checkChain`, no live DB) and
runs a dependency-aware batch of four checks — snapshot parses; chain
linearity (both always run, independent of each other); declarations ↔
snapshot (needs a parsed snapshot); chain tip ↔ snapshot (needs both
priors) — reporting every failure in one multi-diagnostic batch with a
`skipped:` line for any check a failed dependency ruled out, not just
the first failure (D34, redesigned mid-phase from the original
sequential-short-circuit reading once reviewer confirmed the batch path
was cheap to reuse from PR B rather than new infrastructure). `hejbro
init` idempotently scaffolds the config, migrations directory, and an
empty snapshot, reporting skips and always exiting 0 (D35) — the
missing-`entry`-file case doubles as the onboarding surface, its error
carrying a complete example. `examples/cli-smoke` proves the whole loop
end to end against the *built* CLI binary in a tmp copy: init →
generate → generate (no-op) → verify → a column rename that's
ambiguous until resolved by the suggested `--rename` flag → verify
again.

- `hejbro.config.ts` via `defineConfig()`, zod-validated (entry files,
  migrations dir, snapshot path, prefix strategy) (D30)
- TS declaration + config loading through **jiti only** (D29) — the one
  place core purity meets the filesystem
- `hejbro generate`: migration file emission with the banner comment format
  (spec §6.6) plus the new `parent-snapshot:`/`snapshot:` sha256 hash lines
  (D33)
- Non-interactive rename/drop confirmation via repeatable
  `--rename <schema>.<table>.<old>=<new>` / `--confirm-drop
  <schema>.<table>.<column>` flags (rule A; no TTY prompts) (D32)
- `hejbro verify`: four-check snapshot/chain consistency command for CI
  (snapshot parses, declarations ↔ snapshot, chain linearity, chain tip ↔
  current snapshot) (D34)
- `hejbro init`: idempotent scaffold of config + migrations dir + empty
  snapshot (D35)
- Strict SQL identifier validation (`^[a-z][a-z0-9_]*$`) at declaration time,
  required by the rename flag grammar (D36)
- Acceptance: `examples/` project generates end-to-end from the CLI
  (`init` → `generate` → `verify`, including a rename round-trip)
- Brainstorm resolved (2026-08-20, owner-approved): jiti-only loading
  (D29), zod-validated config (D30), citty as the CLI framework (D31),
  flag-based non-interactive renames with rule A (D32), the single
  snapshot file's banner hash chain (D33), `hejbro verify`'s four checks
  (D34), `hejbro init`'s idempotent scaffold (D35), and strict SQL
  identifier validation (D36). Implementation plan:
  `docs/plans/2026-08-20-phase5-implementation.md`. Decision log entries
  D29–D36 record the phase's brainstorm outcomes in full. Landed across
  five PRs against sub-issues of #6: PR #79 (#74, core rename-plan
  engine + identifier validation + banner hashes), PR #80 (#75, CLI
  package foundation + config + loader + diagnostics + `init`), PR #81
  (#76, `generate` command + golden error corpus + golden help output),
  PR #82 (#77, `checkChain` + `verify`, including the mid-phase batch
  -reporting redesign), and this acceptance/close-out work (#78).
  Deferred: an onboarding example schema page, the full rename-rules
  walkthrough, a `hejbro verify` CI example, the `Next:`-marker
  retrofit onto Phase 1–4 errors, `assertSqlName` for explicit index
  names, the `--flag=value` equals-joined token form, and an npm-pack
  install-path smoke test — tracked as Phase 7/8 issues (see below).

## Phase 6 — Supabase preset (`@hejbro/supabase`) ✅

Built strictly on the provider interface — this phase was also the
interface's first real test (spec §4.1: if it needs a core special case, fix
core).

Landed: two pure core additions that grow the public extension interface
from four to five preset contributions (D37), landed *before* any Supabase
code, then `@hejbro/supabase` built entirely on that public surface. A
**validation channel** — `generateMigration({ validators })` runs
preset-supplied pure functions over the built snapshot and normalized
declarations, returning `warnings`; error-severity diagnostics join `errors`
and short-circuit generation exactly like rename errors (D37). An
**`existingTable()` primitive** — a reference-only `Table` usable as an FK
target, in `exists()`, and in view from/joins, but never declared, diffed,
or emitted; passing one to `generateMigration` is the hard error
`existing-table-declared` (D41). Core also gained a branded `Role` type
(D43, non-breaking — `grant().to()`/`rls.policy().to()` widened to
`string | Role`). On top of that surface, `@hejbro/supabase` landed role
presets (`anonRole`/`authenticatedRole`/`serviceRole`), the
`authUid()`/`authJwt()` expression helpers (D45 — plain `auth.uid()`/
`auth.jwt()` calls, no automatic initPlan wrapping), the prebuilt
`authUsers` existing-table reference, three validators (reserved-schema
hard error covering `auth`/`storage`/`realtime`, D38; exposed-table-
without-RLS warning, D40; view-over-RLS-without-`security_invoker`
warning, #66/D39 — `defineView`'s JSDoc now points here instead of
carrying the TODO), and the storage bucket object kind
(`supabase-storage-bucket`, the first row-data kind: `create`/`alter` emit
one idempotent `insert … on conflict (id) do update set …` into
`storage.buckets`; `drop` emits no SQL, and its manual-deletion guidance
now surfaces in the migration banner too — `bannerLabel`'s `drop` case
gained the same `notes.join(", ")` rendering `alter` already had,
additive since no existing drop change ever carried notes, D42). Two
acceptance examples close the phase: `examples/preset-smoke`, a toy
zero-Supabase custom kind (`smoke-schema-note`) plus one expression helper
(`txidCurrent()`) built on `@hejbro/core` alone — proving the extension
interface is generic by construction, not by claim — and a **reduced**
`examples/dd-land` that exercises every preset feature exactly once
(`authUsers` FK, `authUid()` RLS policy, storage bucket, role-preset
grant, the exposed-table warning, and the #66 warning, plus a negative
`schema("auth")` case) through `generateMigration({ registry:
<default + registerSupabaseKinds>, validators: supabaseValidators })`,
golden-asserted end to end (D44 — the full dd.land port stays Phase 7).

- **§4.1's first real test, passed.** Every `packages/supabase` source and

## Phase 7 — Table-kind completeness, local round-trip examples, skills, README

Brainstorm resolved (2026-08-20, owner-approved): decision log entries
D46–D56, plus D57 (naming unification, decided 2026-08-21). Two roadmap changes came out of it: the round-trip runs
**locally via Docker**, not as a CI job (D49), and the showcase examples
are **generic and named by database** — `examples/postgres` and
`examples/supabase` — not a port of any particular project (D53).
Implementation plan: `docs/plans/2026-08-20-phase7-implementation.md`
(written after the owner reviews this section and the spec rows).

Work groups, in PR order:

1. **Table-kind completeness** (D46, D50–D52; #104, #105, #106, #22) —
   CHECK constraints (`check(name, expr)`), partial indexes
   (`.on(...).where(expr)`) and ordered index columns (`desc(t.col,
   { nulls })`), FK `on update` (+ `set default`), self-referencing FKs via
