# D106 evaluation — add-aggregate-filter (round 1)

## Method

Context-free adversarial review of the delta spec only. Inputs read: the
delta text from `npx openspec show add-aggregate-filter --diff`
(`query-builder` — *Selects aggregate and group*; `snapshot-format` —
*Stored query-node decode strictness follows the node's format provenance*),
the built public surface (`packages/*/dist/index.d.ts`, imported as a user
through `hejbro`, `@hejbro/core`, `@hejbro/query`, `@hejbro/pg`),
`skills/hejbro/references/query-layer.md` and `README.md`. Not read:
proposal/design/tasks, `.blackbox/`, `packages/*/src`, `packages/*/test`,
PR or issue bodies, git log messages. (`show --diff` prints the proposal
body above the spec diffs; it was disregarded — every probe below is
derived from a delta sentence or a public signature.)

Worktree: detached at dev `6e2c8aec` (PR #963 merged), `pnpm install
--frozen-lockfile && TURBO_FORCE=1 pnpm build --force`. Probes lived in
`/private/tmp/d106-af/` (a scratch package whose `node_modules` symlinked
the worktree's built packages) and were removed afterwards.

Two axes:

- **Type axis** — one `tsc --strict` file (`exactOptionalPropertyTypes`,
  `moduleResolution: nodenext`): 14 `@ts-expect-error` rejection assertions,
  20 positive result-type assertions (`Equal<…>` for filtered-vs-unfiltered
  identity, assignability for concrete types), 9 must-type-check
  constructs. **43 assertions, 0 unexpected diagnostics, 0 unused
  directives.**
- **Server axis** — one Node script against Docker `postgres:17`
  (PostgreSQL 17.11, container `d106-af-pg`, host port 55590): a schema of
  two tables, one `defineFunction`, one `defineView` whose body carries all
  five filtered aggregates plus a windowed one; migration generated by
  `generateMigration` and applied; seeded with values past 2^53 so bigint
  revival is observable. **124 recorded rows, 40 server executions**
  (rendered SQL applied verbatim; results/error codes recorded).

## Blocking findings

None.

## Non-blocking findings

1. **"the same diagnostic `where` gives" — same code, different text.**
   Requirement text: "fails at build time with the same diagnostic `where`
   gives"; scenario: "fails immediately with `window-function-not-allowed`,
   the same diagnostic `where` gives for the same input". Observed: both
   throw `HejbroError` code `window-function-not-allowed`; the messages
   differ in their first clause —
   `filter()'s condition cannot reference a window function -- Postgres evaluates window functions after FILTER (WHERE …) runs, …`
   vs `a where clause cannot reference a window function — Postgres evaluates window functions after where runs, …`
   (the remainder, including the `Next:` sentence, is identical). The
   scenario's wording pins the code, so this is wording precision, not a
   contradiction: "the same diagnostic code" would say what ships. Also
   observed: the `filter` message uses `--` where the `where` message uses
   `—` (an em dash) — a punctuation inconsistency between sibling messages.
2. **A non-expression target throws a bare `TypeError`, not
   `filter-not-aggregate`.** `filter("count(*)", c)`, `filter(undefined, c)`,
   `filter(null, c)` throw `TypeError: Cannot use 'in' operator to search for
   'exprNode' in …`. For a TypeScript user these are rejected by the type
   (`@ts-expect-error` held for a string target), so "refused at build time"
   holds; only a JS caller or a cast reaches the `TypeError`. `where` behaves
   the same for the same inputs (`TypeError: Cannot read properties of
   undefined (reading 'nodeKind')`), so the "exactly what `where` accepts"
   symmetry is intact. The delta's list ("a column, a computed expression, a
   declared function call, a window-only function, a windowed expression")
   is satisfied for every value the signature admits; a non-`Expr` is
   outside it. Neighbour.
3. **An aggregate inside the condition is not refused at build time.**
   `filter(count(), gt(count(), 1))` and `filter(count(), gt(filter(count(),
   …), 1))` compile and Postgres refuses them: `42803 aggregate functions are
   not allowed in FILTER`. `where` lets the same condition through too
   (Postgres: `42803 aggregate functions are not allowed in WHERE`), so this
   is consistent with "exactly what `where` accepts"; the delta is silent on
   aggregates-in-FILTER, unlike window functions. Recorded so the silence is
   a known one.
4. **Target naming calls a builder builtin a "declared function call".**
   `filter(coalesce(posts.views, 0), c)` → `… and got a declared function
   call "coalesce"`; `now()` → `… "now"`. The delta lists "a computed
   expression"; the message's noun is borrowed from `defineFunction`
   vocabulary. Wording nit; the five constructors and the target are named
   as the requirement demands.
5. **Type-level nullability of every aggregate (pre-existing, unchanged).**
   At the type level `count()` reads back as `bigint | null` — filtered,
   unfiltered, windowed and nested alike (assignable to `bigint | null`,
   not to `bigint`); `min(timestamptz not null)` as `Date | null`;
   `max(bigint)` as `bigint | null`. `query-layer.md`'s table says `count()`
   → `bigint`. The delta's claim — the filtered cell keeps the aggregate's
   own type — holds exactly (`Equal<>` identity for all seven pairs, both
   windowed pairs and the nested pair); the doc/type gap belongs to the
   aggregates themselves, not to `filter`.
6. **Damaged-node message wording.** A stored `aggregate-filter` node missing
   `where` (or `fn`) fails with `malformed-snapshot-node`: `hejbro failed
   while reading a "where" discriminator: unrecognized value "undefined"`.
   It names the missing field as the requirement demands; "discriminator"
   is the wrong noun for a required child slot (the same message shape
   serves `nodeKind`). Cosmetic.
7. **A forged expression object is not caught.** A hand-built
   `{ exprNode: { nodeKind: "functionCall", functionName: "count", args: [] }, family: "numeric" }`
   passes `filter` and renders `count() filter (where …)` (invalid SQL —
   Postgres would refuse `count()` without `*`). Outside every public
   constructor; not a delta claim. Note only.
8. **`exists` drops a subselect's projection before the walker sees it.**
   `filter(count(), exists(select({ r: over(rowNumber(), spec) }, comments)…))`
   compiles to `exists (select 1 from …)` — the window function in the
   subselect's projection never reaches the condition walker, in both
   `filter` and `where`. Postgres accepts the rendered statement (the
   projection is gone), so nothing is wrong; recorded because a reader of
   "a window function inside the condition … fails at build time" might
   expect that input to be refused.

## Scenarios verified

**query-builder / Selects aggregate and group (MODIFIED)**

- *A filtered aggregate renders Postgres's own clause* — verified.
  `count(*) filter (where "app"."posts"."status" = $1)`,
  `sum("app"."posts"."views") filter (where "app"."posts"."views" > $1)`,
  `avg("app"."posts"."views") filter (where "app"."posts"."deleted_at" is null)`,
  plus `min`/`max`/`count(col)`; all six executed on 17.11 (rows
  `2`, `150`, `52.5…`, `2024-01-01…`, `9007199254740995`, `2`). Windowed:
  `count(*) filter (where … = $1) over (partition by … order by … asc)` —
  `over (…)` after the filter clause; executed, running counts `1, 2, 0`.
  Bind order across projection/`where`/`having`/`order by`: `$1…$9` in
  render order with values `["published",1,60,"published","draft",0,"pub%",0,"published"]`;
  executed. Result type: filtered ≡ unfiltered for all seven projections
  (type axis); runtime revival `0n`/`2n` (bigint), `9007199254740993n`
  through `over(filter(max(...)))`, `Date` for `min(timestamptz)`.
- *A window function inside the filter condition is refused* — verified.
  `filter(count(), gt(over(rowNumber(), spec), 1))` throws
  `window-function-not-allowed` synchronously, before any render; identical
  code from `where` for the same input; identical outcome for 7 deeper
  nestings (`and`, `not`, `or`, `` sql`${over(...)} > 1` ``, `between`,
  `inArray`, `coalesce`). Forced through raw SQL, Postgres answers
  `42P20 window functions are not allowed in FILTER`. (Message text: finding 1.)
- *filter over a non-aggregate is refused at build time* — verified. A
  column reference, `` sql`1` ``, a `db.fn` call (a thenable — refused
  synchronously, "got a thenable, not an expression -- a function called
  through db.fn is one"), `rowNumber()`, `over(count(), spec)` — each
  `filter-not-aggregate`, message naming `count(), min(), max(), sum() or
  avg()` and the target ("a column reference", "a raw sql fragment", "a
  window function", "an already-windowed expression"); nothing rendered.
  Also refused with the same code: `rank()`, `over(rowNumber())`,
  `over(filter(...))` (the reverse composition — "already-windowed"),
  `filter(filter(...))` ("already-filtered"), `coalesce(...)`, `now()`,
  `literal(true)`, `exists(...)`, `jsonArrayFrom(...)`, `eq(...)`. Type
  axis: `rowNumber()`, a `db.fn` call, a string and a subselect stage are
  rejected by `tsc` before runtime; a column, a `sql` fragment, a windowed
  expression and a double filter type-check and are refused at build time.
- *Grouping with a group filter* / *having is unavailable without grouping*
  — unchanged by the delta; exercised incidentally (`groupBy` → `having`
  with a filtered aggregate inside `having` and `orderBy` both render and
  execute).
- Requirement prose, additionally: "The condition SHALL accept exactly what
  `where` accepts" — 18 conditions gave the identical build-time outcome
  under `filter` and `where` (14 accepted; a text column accepted by both
  and refused by Postgres `42804 argument of FILTER must be type boolean,
  not type text`; string/number/`undefined` `TypeError` in both — finding
  2). Postgres accepted a correlated `exists` and a scalar subselect inside
  FILTER (`ACCEPTED rows=[{"count":"2"}]`).

**snapshot-format / Stored query-node decode strictness (MODIFIED)**

- *A damaged aggregate-filter node is refused, not repaired* — verified.
  Stored node shape `{"nodeKind":"aggregate-filter","fn":{…function-call…},"where":{…}}`;
  removing `where` → `malformed-snapshot-node … reading a "where" …
  unrecognized value "undefined"`; removing `fn` → `… "fn" …`; `fn: null`,
  `where: null`, `fn` replaced by a column-ref node, `where` replaced by a
  string — all refused naming the slot; the same node damaged inside a
  `window` node's `fn` slot — refused. An unknown extra field is ignored
  (decoded normally). Never repaired into a value.
- Requirement prose: token `"aggregate-filter"` appears 6× in the rendered
  snapshot (once per filtered projection, including the one under
  `window.fn`), 0× camel-case; `renderSnapshot(parseSnapshot(rendered)) ===
  rendered`; `encodeQueryNode(decodeQueryNode(stored))` byte-identical;
  `formatVersion` is `8` in the built snapshot, `HEJBRO_SNAPSHOT_VERSION ===
  8`, and both `examples/*/hejbro.snapshot.json` carry `8`.

**Neighbours exercised (no delta sentence; all behaved)**

- Nested reads: a filtered `count`/`max(bigint)` inside `jsonObjectFrom` is
  cast `::text` exactly as the unfiltered form and revived as `bigint`
  (`9007199254740997n`); `min(timestamptz)` revived as `Date`; a windowed
  filtered aggregate inside `jsonArrayFrom` cast `over ()::text` and
  revived. Empty collection → `[]`, missing object → `null`.
- CTE body, `distinct`, `` sql`${filter(count(), c)} * ${2}` `` (renders
  `count(*) filter (where … = $1) * $2`, result `4`) — all executed.
- View body: `create or replace view` carries the filter clauses with
  inline literals; renaming `posts.status → state` with `--rename`
  retargets all 6 stored column references inside the filter conditions
  (`state` 6, `status` 0), emits only the `alter table … rename column`,
  and a regeneration from the new snapshot is a no-op (`hasChanges=false`).
  The view reads correctly afterwards.
- Postgres's own refusals for shapes the builder makes unrepresentable:
  double filter `42601`, filter after over `42601`, filter on `now()`
  `42809 FILTER specified, but now is not an aggregate function`.
- Documentation: `query-layer.md` §`FILTER (WHERE …)` matches shipped
  behaviour (rendered text, composition order, refusal list and code).
  `README.md` does not mention `filter` (no delta sentence requires it).
- `npx openspec validate add-aggregate-filter --strict`: valid.

## Verdict

**ARCHIVE** — 0 blocking, 8 non-blocking. Type axis 43 assertions (0
diagnostics); server axis 124 recorded rows over 40 executions on
PostgreSQL 17.11. Error codes recorded: `42803` (aggregate in FILTER /
WHERE), `42P20` (window in FILTER), `42601` (double filter; filter after
over), `42809` (FILTER on a non-aggregate), `42804` (non-boolean FILTER
argument).
