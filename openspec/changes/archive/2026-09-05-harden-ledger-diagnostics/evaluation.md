## BLOCKING

### B1 — `apply-ledger-unreadable` drops the role when the connection is lost, an input class the requirement enumerates

**Setup** (`ts`, `tt`): a ledger the connection may read; another session holds
`lock table hejbro.migration_ledger in access exclusive mode`, so hejbro's read
waits. The waiting backend is then killed two ways.

```sql
-- session A
begin; lock table hejbro.migration_ledger in access exclusive mode; select pg_sleep(12); commit;
-- while hejbro waits:
select pg_terminate_backend(pid) from pg_stat_activity where datname='ts' and wait_event_type='Lock';
```

**Command** `DATABASE_URL=postgres://postgres:pw@127.0.0.1:15901/ts hejbro status`

**Observed** (exit 1, stderr):

```
error[apply-ledger-unreadable]: "hejbro"."migration_ledger"
  `"hejbro"."migration_ledger"` could not be read (57P01): terminating connection due to administrator command. …
  Next: grant the connecting role `select` on … , or connect as the role that applied, then rerun `hejbro status`.
```

Same shape with `docker kill d106-ld-pg` mid-read — the "failure carrying no
server code at all" case:

```
  `"hejbro"."migration_ledger"` could not be read: Connection terminated unexpectedly. …
```

In both, the role is absent from the diagnostic and the `Next:` line degrades to
the anonymous "the connecting role".

**Scenario sentence judged against** (MODIFIED *Migrations are applied in chain
order…*, requirement prose):

> Every other answer the server gives to a read hejbro sends to the ledger — a
> role that may connect but may not select from the table, a schema whose
> `usage` is withheld, **a failure carrying no server code at all** — SHALL be
> reported with the one shared code `apply-ledger-unreadable`, naming the ledger
> by its qualified name, **the role the connection authenticated as**, and the
> server's own code and message unsummarized …

The sentence names the no-server-code case explicitly and still requires the
role. The role is not "unknowable" here: the **write** side of the same change
names it under the very same failure. Killing the backend while the ledger
`insert` waits (`ty`, `lock … in exclusive mode` + `pg_terminate_backend`) gives

```
error[apply-ledger-unwritable]: "hejbro"."migration_ledger"
  writing `"hejbro"."migration_ledger"` was refused as the role "postgres" (57P01): terminating connection due to administrator command. …
```

— identical `57P01`, identical connection death, role present. The read
renderer, whose failing statement is the first query on the connection,
apparently never learned it; the write renderer had. Under the delta's plain
reading the read path is required to name it too, and can.

**Verdict: BLOCKING.** All four `#### Scenario:` blocks of the change pass (see
OK-2, OK-3, OK-14); it is the requirement's own universal sentence, on the input
class it names, that shipped behaviour does not meet. If the enumeration is
meant as "name what there is" (as it must be for the server code, which is
genuinely absent in the `docker kill` case), the finding downgrades to
NON-BLOCKING — but then the sentence should say so, because the role *is* there.

## NON-BLOCKING

### N1 — a healthy `migrate` of five or more migrations prints a Node memory-leak warning on stderr

**Setup** (`tg`, `tj`): an empty database and the 5-file chain; no fault of any
kind injected.

**Command** `DATABASE_URL=…/tg hejbro migrate`

**Observed** (exit 0, stdout reports all five applied; **stderr**):

```
(node:40240) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 error listeners added to [Client]. MaxListeners is 10. Use emitter.setMaxListeners() to increase limit
(Use `node --trace-warnings ...` to show where the warning was created)
```

Deterministic and threshold-pinned: a run applying **4** migrations (`tj`, the
first migration pre-recorded by hand) is clean; **5** warns, every time, in both
processes of the concurrent-run test (`tk`) as well. `status` never warns.

The warning names `[Client]` and counts `error` listeners — the shape of a
listener attached per pool checkout and never removed on release, which is
exactly the mechanism this change's Impact describes adding. A real project with
more than four pending migrations meets it on every clean run: the tool's own
stderr tells the user it is leaking. The delta says nothing about it, so this
contradicts no scenario — but "no raw runtime noise reaches the user" is the
spirit of the surrounding requirement, and this is Node's own diagnostic leaking
through the same channel the change was built to keep clean.

### N2 — every `apply-ledger-unreadable` `Next:` line is permission-shaped, including for causes no grant can fix

**Setup** (`tt`): `alter role r_to set statement_timeout = '1500ms'`, another
session holding `access exclusive` on the ledger.

**Command** `DATABASE_URL=postgres://r_to:pw@…/tt hejbro status` (exit 1)

**Observed**:

```
  `"hejbro"."migration_ledger"` could not be read as the role "r_to" (57014): canceling statement due to statement timeout. …
  Next: grant that role `select` on `"hejbro"."migration_ledger"` and `usage` on the `"hejbro"` schema, or connect as the role that applied, then rerun `hejbro status`.
```

The same fixed `Next:` follows the two connection-loss cases of B1. Neither is
answered by a grant or by another role; the reader is sent to change privileges
that were never the problem. The delta does prescribe this line — "ending with a
`Next:` line that offers both ways out: grant that role what the read needs, or
connect as the role that applied" — so shipped behaviour follows the letter. The
gap is in the sentence: it was written for the permission family and is now
applied to a `57014`/`57P01`/socket-death family the same requirement admits.

### N3 — "the ledger records nothing new" contradicts the same run's own stdout

**Setup** (`ua`): three migrations applied, `fourth` and `fifth` pending,
`alter table hejbro.migration_ledger add constraint no_fifth check (filename not like '%fifth%')`.

**Command** `DATABASE_URL=…/ua hejbro migrate` (exit 2)

**Observed** — stdout:

```
migrate: applied 1 migration(s):
 - 20260905013907_fourth.sql
```

stderr:

```
error[apply-ledger-unwritable]: … (23514): new row for relation "migration_ledger" violates check constraint "no_fifth". What was refused is the row recording "20260905014132_fifth.sql", … so nothing from "20260905014132_fifth.sql" is applied and **the ledger records nothing new**. …
```

Verified in the database: the ledger now holds four rows, one of them written by
this run. The clause is true of the failing file and false of the run; a reader
who takes it at face value will not go looking for the row `fourth` just
committed. Nothing in the delta forbids it — the scenario only asks that no
migration file be named as what failed, which holds.

### N4 — an RLS-forced ledger reads back empty, and the run is then billed to a migration file

**Setup** (`tr`): the ledger owned by a non-superuser (`r_rls`), three
migrations recorded, then

```sql
alter table hejbro.migration_ledger enable row level security;
alter table hejbro.migration_ledger force row level security;   -- no policies
```

**Commands** (as `r_rls`):

```
hejbro status  → exit 0
status: the ledger table exists and records no migrations yet.
status: 5 migration(s) pending: …

hejbro migrate → exit 1
error[apply-failed]: 20260905013727_first.sql
  applying "20260905013727_first.sql" failed (42P06): schema "app" already exists. …
```

The server raises no error — RLS filters the rows — so "Reading the ledger SHALL
fail in hejbro's own terms or not at all" is not contradicted: it did not fail.
But the outcome is the exact shape #823 set out to remove, reached by a route the
delta does not cover: a ledger hejbro cannot really see, a report that says the
database has recorded nothing, and a failure charged to a migration file that is
not at fault. (With a superuser the same setup is invisible — superusers bypass
`force`, so `status`/`migrate` behave normally; the trap only springs for the
least-privileged role, which is the one a careful operator uses.)

### N5 — `raise`'s bootstrap refusal says "no migration statement was sent" though `raise` sends no migrations

**Setup** (`t7`): empty database, role `r_boot` with `connect` only (no
`create`).

**Command** `DATABASE_URL=postgres://r_boot:pw@…/t7 hejbro raise --file vendored.sql` (exit 1)

**Observed**:

```
error[apply-ledger-unwritable]: "hejbro"."migration_ledger"
  writing … was refused as the role "r_boot" (42501): permission denied for database t7. What was refused is the ledger's own bootstrap, hejbro's own bookkeeping — **no migration statement was sent**. …
```

`raise` applies a vendored snapshot SQL file, not a migration; the reassurance
names an artifact this command does not have. The delta requires the diagnostic
to name "which write was refused" (it does, correctly: the bootstrap) and is
silent on the rest of the sentence. Same sentence, correct, on the `migrate`
path.

## OK

Each entry names the input, the command, and the delta sentence it satisfies.

**OK-1 — the healthy path is untouched.** `t1` (3 migrations) and `tg` (5): a
normal role, `status` → "no ledger table exists yet", `migrate` → exit 0 with
every file listed, `status` → all recorded, nothing pending. *("Breaking: none
for a database hejbro can read and write.")*

**OK-2 — a read the role may not make, on all three reading commands.** `t1`
with `r_sel` (`usage` on `hejbro`, no `select` on the ledger) and `r_nousage`
(no `usage` on the schema). `status` exit 1, `migrate` exit 2, `raise` exit 1 —
each `error[apply-ledger-unreadable]: "hejbro"."migration_ledger"`, naming the
role (`r_sel` / `r_nousage`), the code (`42501`) and the server's message
verbatim (`permission denied for table migration_ledger` /
`permission denied for schema hejbro`), with a `Next:` line, no driver object,
no stack frame. *(Scenario "A ledger the connected role may not read is reported
in hejbro's own terms"; scenario "status reports a ledger it may not read".)*

**OK-3 — column-level grants only.** `tv`, role `r_col` with
`grant select (id, applied_at)` and `grant insert (id, filename)` and nothing
else: `status` exit 1 / `migrate` exit 2, `apply-ledger-unreadable`, role and
`42501` named. An adversarial neighbour of the two grant shapes the scenario
lists; classified identically.

**OK-4 — the bootstrap's `create` refused.** `t7`, role `r_boot` with `connect`
only. `migrate` exit **2**, `raise` exit 1, both
`apply-ledger-unwritable` … "What was refused is the ledger's own bootstrap"
(`42501: permission denied for database t7`). `status` on the same database is
unaffected (exit 0, "no ledger table exists yet") — a read that finds nothing is
still a state. *(Scenario "A ledger write the database refuses is attributed to
the ledger", the bootstrap clause.)*

**OK-5 — the measured case: `id` without identity and without default.** `t3`,
a hand-built ledger with the four bootstrap columns and
`id bigint not null` only. `migrate` exit **2**:

```
error[apply-ledger-unwritable]: "hejbro"."migration_ledger"
  writing … was refused as the role "postgres" (23502): null value in column "id" … What was refused is the row recording "20260905013727_first.sql" … the statements from that file ran in the same transaction and rolled back with it, so nothing from "…first.sql" is applied … The ledger's "id" column has no identity and no default; the ledger hejbro bootstraps declares it `bigint generated always as identity`, so hejbro never supplies that value itself. Next: …
```

Rollback verified in the database: `select count(*) from hejbro.migration_ledger`
→ 0, `schema app` absent. The header names the ledger, never the file. *(Scenario
"A ledger write the database refuses…"; "A migration is applied atomically with
its own ledger row".)*

**OK-6 — `insert` withheld.** `t4`, role `r_ins` (`select` yes, `insert` no,
owner of `schema app`): `migrate` exit 2, `apply-ledger-unwritable`,
`42501`, "the row recording …fourth.sql"; ledger still 3 rows, `app.marks`
absent afterwards.

**OK-7 — a constraint and a trigger on the ledger reject hejbro's row.** `t6`,
`check (filename not like '%fourth%')` → `23514`; `t5`, a `before insert`
trigger raising `P0001 ledger is frozen by policy` → the server's own message
verbatim. Both `apply-ledger-unwritable`, exit 2. *(The scenario's "a constraint
or trigger on the ledger rejects the row".)*

**OK-8 — the filename is already recorded (a real race).** `tf`: hejbro blocked
mid-transaction on `lock table app.posts in access exclusive mode`; while it
waited, another session inserted the row for the same file. On release:
`apply-ledger-unwritable`, `23505 duplicate key value violates unique constraint
"migration_ledger_filename_key"`, exit 2, nothing applied. *(The scenario's
"because the filename is already recorded".)*

**OK-9 — a ledger altered under hejbro in two further ways.** `ta`,
`alter column applied_at drop default` → `23502`, plus the tailored sentence
"The ledger's "applied_at" column has no default; the ledger hejbro bootstraps
declares it `timestamptz not null default now()`". `tb`, an extra `not null`
column with its default dropped → `23502` plus "that is a column the ledger's
bootstrap does not declare, so hejbro cannot say what value it expects there".
Both exit 2, both name the ledger. `status` against `tb` still reads and reports
normally, as it should — the extra column does not disqualify the ledger.

**OK-10 — a ledger write that found no ledger.** `tn`: an event trigger on
`ddl_command_end` renames the ledger inside the applying transaction, between
the migration's `create table` and hejbro's `insert`. `migrate` exit 2,
`apply-ledger-unwritable`, `42P01 relation "hejbro.migration_ledger" does not
exist`; afterwards the ledger is back at its name (the rename rolled back),
`app.marks` absent. Absence is a state for reads and a failure for writes,
exactly as the delta distinguishes them.

**OK-11 — a refused clearing of the ledger names the ledger, and the rollback is
real.** `t2`, role `r_drop` owning every declared object, `select` but no
`delete` on the ledger, `reset --confirm-drop t2:4` → exit 1:

```
error[apply-ledger-unwritable]: "hejbro"."migration_ledger"
  writing … was refused as the role "r_drop" (42501): permission denied for table migration_ledger. What was refused is the clearing of the ledger's rows … the drops ran in the same transaction and rolled back with it, so every declared object is still standing. …
```

Verified: `app.posts`, `app.tags`, `app.notes` all present, ledger still 3 rows.
No declared object named as the failure. *(Scenario "A refused clearing of the
ledger names the ledger".)*

**OK-12 — the `reset` race is a ledger write, not a drop that failed.** `tp`: an
`on sql_drop` event trigger renames the ledger while `reset`'s own drops run.
Result: `apply-ledger-unwritable` with `42P01`, exit 1, `reset-drop-failed` not
used, and everything standing afterwards (ledger back at its name with all 5
rows, `app.posts` present). *("…including the race in which the relation at the
ledger's name disappears between the identity judgement and the clearing, which
is a ledger write that found no ledger, not a drop that failed.")*

**OK-13 — which half failed decides which artifact is named, structurally.**
Three neighbours:

- `tc`, `app.marks` planted beforehand → `error[apply-failed]:
  20260905013907_fourth.sql`, `42P07 relation "marks" already exists`, exit **1**.
- `td`, role `r_nocreate` with `insert` on the ledger but no `create` on
  `schema app` → still `error[apply-failed]`, `42501 permission denied for
  schema app`, exit 1. The same code (`42501`) that produces
  `apply-ledger-unwritable` on the other half, so the split cannot be
  message-matching.
- `te`, a *raised file* whose own statement writes an invalid ledger row →
  `error[apply-failed]: hejbro raise`, `23514 … migration_ledger_origin_check`,
  exit 1. A ledger-touching statement that is the user's, not hejbro's, is not
  reclassified.

Ledger rows and objects unchanged in each. *(Scenario "The half that failed
decides which artifact is named"; "Which half failed SHALL be established
structurally … never by matching the failure's message".)*

**OK-14 — a lost connection is rendered coded, not a crash.** Read side (`ts`,
`pg_terminate_backend` of the waiting backend; and `docker kill d106-ld-pg`
mid-read): `apply-ledger-unreadable`, exit 1, `57P01` / no code at all, no
`Emitted 'error' event`, no stack. Write side (`ty`, backend killed while the
ledger `insert` waited): `apply-ledger-unwritable` `57P01`, exit 2, rollback
complete. `statement_timeout` (`tt`, `57014`) likewise on both `status` (1) and
`migrate` (2). *("No error the server raised on the ledger SHALL reach the user
as a driver object or a stack trace" — satisfied; the role omission on the read
side is B1.)*

**OK-15 — the boundaries hold.** Probed as adversarial neighbours of the
universal claims:

- *"the relation's absence is a state … whether it was absent all along or
  vanished between the judgement and the read"* — `uc`: an uncommitted
  `drop table` holding `access exclusive` while `status` runs. Judgement sees the
  ledger, the read finds it gone → "no ledger table exists yet", exit 0. Also
  verified that Postgres answers `42P01 relation "x.y" does not exist` for a
  missing schema as well as a missing table (`nosuchschema.migration_ledger`),
  and that a `hejbro` schema with no ledger table (`tx`) reports the same state.
- *which commands read the ledger* — `verify` opens no connection at all (exit
  0 with a `DATABASE_URL` pointing at an unreadable ledger); `check` runs its
  whole catalog comparison against a role with no `select` on the ledger and
  never mentions it; `reset` succeeds end to end as a role with `delete` but no
  `select` (`tu`, exit 0, "dropped every object … and cleared the ledger") — it
  writes the ledger, it does not read it. Only `status`, `migrate` and `raise`
  read, as the delta says.
- *`apply-ledger-occupied` still wins where it should* — `tw`, a view carrying
  the four bootstrap columns at the ledger's name: `status` exit 1 / `migrate`
  exit 2, `apply-ledger-occupied` naming the view and its columns, no read
  attempted, no raw error.
- *concurrency* — `tk`, two `migrate` processes started together on an empty
  database: one applies all five, the other reports "5 migration(s) another run
  already applied while this one waited", both exit 0, no duplicate-key error.
- *partial progress survives a ledger failure* — `ua`/`ub`: stdout lists the
  migration this run did apply while stderr carries the failure; exit **2** when
  the ledger refused, **1** when the migration itself failed, from the same
  starting state. *("`migrate`'s exit code SHALL distinguish three answers … A
  ledger failure is two and not one.")*
- *no raw output anywhere* — every captured stdout/stderr across the 26 inputs
  swept for stack frames, `node_modules` paths, and driver-object fields
  (`severity:`, `routine:`, `[Object`): zero hits. The only stderr text outside
  hejbro's own `error[...]`/`warning[...]` shape in the whole review is N1's Node
  warning.

## Round 1 disposition

Lead-run under the owner's delegation (`.blackbox/412/` D12/D13; ruling `.blackbox/836/` R8).

- **B1** — repaired here (tasks.md 3.1): a client whose connection died is discarded on release, so the classifier's `select current_user` runs on a fresh connection and the read diagnostic names the role after a terminated backend, as the write side already did. When no connection can answer (the server is gone) the role clause is omitted, and the requirement now says so.
- **N1** — repaired here: the client error listener is attached once per client object, never per checkout; a healthy long run prints no MaxListeners warning.
- **N2** — repaired here: the read `Next:` follows the reason class — a refused permission offers the grant or the applying role, a dead connection / cancelled statement / code-less loss offers a rerun; the requirement sentence says so.
- **N3** — repaired here: "the ledger records nothing for that file" (the run may well have applied earlier files).
- **N5** — repaired here: the bootstrap rollback sentence says "no statement from any file was sent" (`raise` applies a snapshot file, not a migration).
- **N4** — forced row-level security makes the ledger read empty without any server error → already #865.

Archived at this disposition.
