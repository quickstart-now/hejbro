# Proposal: add-apply-engine

## Why

hejbro writes SQL and hands it to something else to run. That something
else is where the single-writer model leaks. The declarations are truth
on disk; the database's state is established by a tool hejbro does not
control, in an order hejbro does not observe, leaving a record hejbro
cannot read. Every statement this tool makes about a project is
therefore true of the *repository* and only presumed of the *database*.

The project's own shipped documentation says so, in the section it wrote
for users who hit the gap:

> hejbro's own generated SQL carries no `begin`/`commit` wrapper of its
> own — every migration file (the banner example above included) is a
> plain sequential list of DDL statements — so whether a mid-file failure
> leaves only the earlier statements applied, or gets rolled back
> entirely, depends on whether *the apply tool itself* wraps the run in a
> transaction. hejbro has no way to know which happened, and no way to
> inspect the live database to find out.
>
> — `skills/hejbro/references/generate-verify-workflow.md:100-107`

The first two clauses are facts about the emitted files and stay true.
The last one is a gap, and this change closes it.

D12 priced the boundary deliberately: applying belongs to the user's
pipeline, which keeps core pure and avoids owning credentials. Two of
the three things that price rested on have moved.

- **The credential boundary is already crossed.** `check` opens a
  connection named by `--url`/`DATABASE_URL`, acquires its driver
  dynamically, and refuses to read a connection string from the
  committed config file. The rules for holding a database URL exist and
  are shipped; a second command that connects adds no new class of
  exposure.
- **Core purity is not what this trades.** The engine itself lives where
  the filesystem already lives, in `packages/cli`. `@hejbro/core` is
  touched, but only by the generator-side split described below, which
  is a pure transformation over declarations like everything else there:
  no filesystem, no database, no new runtime dependency.

What has not moved is the reason a boundary was drawn at all, and this
change does not pretend otherwise: applying migrations to a production
database is the most consequential thing this tool can do, so the
contract for *how it fails* is the feature. The happy path is a loop.

**Identity.** hejbro works from declarations and does not read
infrastructure facts to form judgements. Applying is a write in the
direction of the declarations, and the ledger of what it applied is the
record of its own writes. Neither is introspection. The standing ruling
that hejbro does not build database-shape validation is untouched: this
change never asks the catalog what the schema looks like.

## What changes

- **`hejbro migrate`** — applies the migrations on disk that the
  database's ledger does not record, in chain order, recording each as
  it goes. Production included.
- **`hejbro status`** ⟦DESIGN⟧ (name, and whether it is its own command)
  — what the ledger records, what is pending, and where the chain on
  disk and the ledger disagree.
- **`hejbro reset`** — the destructive path, whose refusal contract is
  the larger half of it (below).
- **Standing an empty database up from a snapshot SQL file** ⟦DESIGN⟧
  (name) — generalized deliberately: the command takes a snapshot SQL
  file and an empty database. That a consumer repository's vendored file
  is the common source is a convention and a config default, not a
  coupling; this change builds nothing that depends on the sibling
  change's artifacts.
- **The ledger** — a table hejbro creates and writes, holding one row per
  applied migration.
- **`baseline` gains its registrar.** The `-- baseline:` banner line has
  had a specified consumer and no implementation: "a tool deciding
  whether to run the migration or register it as applied." This change
  is that tool.

## What this change refuses to do

- **It does not validate the database's shape.** The ledger says what
  hejbro applied; it never says what the schema now is. `check` remains
  the only command that reads the catalog.
- **It does not parse SQL.** This repository states it contains no SQL
  parser, and that is an asset, not an accident. Re-reading our own
  emitted files to recover what we knew when we wrote them is
  introspection pointed at our own output — the same anti-pattern as
  reading `dist` to learn about `src`. Whatever the engine needs to know
  about a migration file, it knows at emit time or reads from a banner
  line written at emit time.
- **It does not roll back.** No inverse is generated by this tool and
  nothing in the chain describes one. Recovery from a failed apply is a
  forward operation, and saying so is part of the contract rather than
  an omission from it.
- **It does not become the only way to apply.** A user whose platform
  applies migrations is not made wrong by this change. What hejbro owes
  them stops at the registration semantics `baseline` already promised;
  general interoperability with other appliers is deferred.

## The contract this change is actually about: partial failure

> **A premise this section was drafted on turned out to be false, and
> the correction is recorded rather than quietly repaired.** The premise:
> `alter type … add value` cannot run inside a transaction block,
> therefore a whole-run transaction is impossible. That is PostgreSQL
> 11's rule. PostgreSQL 12 and later execute it inside a block and forbid
> only *using* the new value before the transaction commits — measured
> here on PG17, not merely read: the statement succeeded inside a
> transaction, rolled back cleanly when the transaction did, and using
> the value in the same transaction failed with
> `55P04 unsafe use of new value "…" of enum type …`. That error text is
> the one the engine's own diagnostic has to translate, and its remedy is
> a second migration. So atomicity is not impossible; whether it is
> *available* is an owner decision about the supported Postgres floor,
> which this repository has never stated.

Even with per-file atomicity, a run applies several migrations, so a run
that stops at the third leaves the first two applied. Partial failure
moves from inside a file to between files; it does not disappear. And
the applier this project ships today already produces the finer kind:
`psql` with `ON_ERROR_STOP=1` and no transaction wrapper commits every
statement before the one that failed — and nothing records that it
happened.

So the contract is not the happy path; it is:

- what unit is applied atomically,
- what the ledger says after a run that stopped halfway,
- and what the user's *next command* is.

The last is the AI-native requirement in operational form: truth is the
committed files, verification is an exit code, and a failure names the
command that follows it. An engine that fails with a Postgres error and
no next step fails that test — the user is left reconstructing, by hand,
which statements ran.

**There is already an applier in this repository, and it is `psql`.**
`scripts/roundtrip.sh:22-24,37-41` applies an example's committed chain
one file at a time:

```
psql() { docker exec -i "$CONTAINER" psql -U postgres -v ON_ERROR_STOP=1 -q "$@"; }
…
for f in "$EXAMPLE_DIR"/migrations/*.sql; do
  psql -d chain < "$f"
done
```

So the semantics the committed chains have actually been verified
against are: statement at a time, no transaction wrapper, stop at the
first error — and the thing that found the statement boundaries was
psql's lexer, not our code. The question this change faces is therefore
not "shall we start splitting SQL"; it is "what replaces the lexer we
have been borrowing". An engine that sends a file whole through a driver
is a *different applier* from the one the examples were verified with,
and that difference is a contract change rather than an implementation
detail.

## Open design forks

Carried into `[design]` tasks and settled with the owner before code.
Each states the trade, not a preference.

### DA — Who writes the ledger row — **settled: the engine does**

The fork was between the migration SQL carrying its own `INSERT` and the
engine writing the row. It is closed here rather than carried into a
`[design]` task, because measurement answered it.

- *SQL-carried*: the file records itself no matter what ran it, so a
  database applied by another tool still has a ledger. The cost: the
  row's content is fixed at generation time, the table must be
  bootstrapped by the file itself, and the row can only mean "the file
  ran to the end" if the file is atomic — which is exactly what the
  section above says it cannot be.
- *Engine-written*: the writer knows what happened, so a row can record
  a stopped run, and registering a baseline *without running it* is
  expressible at all. The cost: only hejbro's engine records, and a
  migration applied by another tool is invisible to the ledger.

**Prior art is unanimous and the reason matters more than the count.**
Six tools were examined and six write the row from the engine; none puts
it in the migration SQL. Two are decisive rather than merely numerous:
drizzle-kit executes the migration's statements and the ledger insert
inside one `session.transaction`, and Prisma writes its row *before*
applying the migration — a shape a statement inside the file cannot
have, at any cost. And the columns that let Atlas resume from the
failed statement (`applied`, `total`, `error_stmt`) are values only the
executing engine holds.

**The four requirements handed over are not inherited automatically, and
re-judging them settles most of this fork.**

- *A migration can carry the schema it produced* — its own text is the
  most literal statement of the premise D12 just retracted: "hejbro
  SHALL write these statements and SHALL NOT execute them. No command
  acquires a database connection in order to record a manifest row."
  **Dies with the premise.**
- *The bootstrap is idempotent and precedes the insert* — **survives,
  changed in kind.** It had to repeat in every file only because no one
  knew where a chain would be started from. An engine bootstraps once
  per run; idempotence stays, per-file repetition goes.
- *The database owns the order of rows* — **survives unchanged**, and
  changes what it defends against. Written for a manifest, it forbade a
  file from supplying its own ordering value; read for a ledger, it
  forbids the *engine* from supplying one. The old implementation paid
  for it with `seq bigint generated always as identity` and
  `applied_at timestamptz default now()`, neither ever supplied by the
  insert.
- *A baseline migration carries no manifest row* — **dies, and it is
  the clearest evidence for engine-written.** It exists only as a
  consequence of the writer being the SQL: a baseline is registered
  rather than run, so an insert inside it never executes, so the
  product had to *explain* to users that the ledger would stay empty
  until the next migration. Move the writer to the engine and the
  requirement has nothing left to say — registering a baseline becomes
  writing a row without running the file, which is what the genre does.

One consequence of choosing SQL-carried that is easy to miss: the
sibling change ended a requirement about embedding a payload safely with
the note "A file has no terminator to escape." Putting the row back
inside the SQL brings that problem back with it, along with the
dollar-quote guard and the refusal code the old implementation needed.

**Settled: the engine writes the row, inside the same transaction that
applies the file.** What stays for `[design]` is the row's shape and
where the table lives (DC), not who writes it.

### DB — What unit is applied, and how the engine knows

A statement-aware splitter is excluded on principle (see "It does not
parse SQL"). What remains was settled by measurement against a real
`postgres:17`, driving `packages/pg`'s own driver source
(sha256-matched to the file at this commit) rather than arguing from it.

**The file is the unit, sent whole through `transaction()`.** The
measurements, each with what it establishes:

- A committed example migration — 6975 bytes, 50 semicolons, a
  `$function$` body among them — went through one `execute` inside
  `transaction()` and created every table, view, trigger, policy, grant
  and function it declares. **Dollar-quoted bodies survive being sent as
  one string**; nothing needs to find their boundaries.
- A file whose second statement fails leaves **nothing** behind: the
  first statement's table does not exist afterwards. Multi-statement SQL
  with no parameters travels as a simple query, and the server wraps it
  in an implicit transaction block — confirmed a second way, with a
  three-statement file whose first two succeeded and whose third divided
  by zero: all three vanished.
- A ledger row inserted in the same transaction as the file **rolls back
  with it**. A failed apply leaves no trace in the ledger; a successful
  one leaves exactly one row.

This is not the applier this project has been using, and the difference
is the contract: `psql -v ON_ERROR_STOP=1` with no wrapper commits every
statement before the failing one. **Adopting the driver path replaces
statement-at-a-time semantics with per-file atomicity.** It is a
strictly stronger guarantee, and it is still a change of meaning that
this proposal states rather than absorbs.

**What the resolution costs.** The engine can say *which file* failed
and repeat the server's own error — code, message, routine, and
sometimes a character position — but it cannot say "statement 7". The
errors measured are specific enough to be useful on their own
(`42P07 relation "t2_a" already exists`;
`55P04 unsafe use of new value "awful" of enum type mood`, position 8).
Whether the engine converts a position into a pointer into the file is a
`[design]` question about the report, not about the applier.

**Two conditions become contract, because both were measured breaking
things silently:**

- **Statements go out with no parameters.** With `params: []` the driver
  takes the simple-query path and multi-statement SQL is legal; add a
  single parameter and the same string is refused with
  `42601 cannot insert multiple commands into a prepared statement`.
  The ledger insert is therefore its own `execute` inside the same
  transaction, where parameters are welcome because it is one statement.
- **An applied file carries no transaction-control statement.** A
  `commit;` in the middle of a file silently ends the atomicity: the
  statements before it survived and the ones after it rolled back, with
  no error and no warning. Worse, a failed file containing its own
  `begin` **poisons the pooled connection** — the two following calls on
  the same driver both failed with
  `25P02 current transaction is aborted`, because the `execute()` path
  releases a client after a failure without rolling back (the
  `transaction()` path has a handler for exactly this and `execute()`
  has no counterpart). hejbro's generator emits no such statement today;
  a hand-edited file can. That makes it a precondition the engine
  states, not an assumption it inherits.

### One migration this project already emits does not survive the wrap

Per-file atomicity is a stronger guarantee everywhere except one place,
and that place is not hypothetical: **hejbro's own generator produces a
file that applies cleanly under today's applier and fails under the
proposed one.**

Adding an enum value and, in the same run, a column defaulting to that
value emits — from `generateMigration`, not from a hand-written
fixture — exactly this, with no error and no warning:

```
alter type "app"."mood" add value 'great';

alter table "app"."t" add column "flag" "app"."mood" default 'great';
```

`psql -v ON_ERROR_STOP=1` applies it and exits 0. Wrapped in a
transaction it fails with `55P04 unsafe use of new value "great" of enum
type app.mood`, rolls back correctly, and leaves nothing applied. The
ordering is structural rather than accidental: table statements declare
`dependsOn: ["schema", "enum", "sequence"]`, so an enum statement always
precedes the table statement that uses it.

The trigger is narrow and was measured on three variants — a column that
does not reference the new value passes, a default naming an *existing*
value passes, and the same two statements in two transactions pass.

**But "the new value appears in the file" is the wrong test, and
measurement is what showed it.** Seven surfaces were driven end to end,
from declaration through the generator's own SQL to a real server: a
column default, a check constraint, an index predicate, a generated
column, a view body and a policy predicate all fail with the same
`55P04`. A `plpgsql` function body containing the identical literal
**succeeds** — its body is not parsed when the function is created. A
trigger built on the file's text would split a migration that never
needed splitting.

So the condition is about *where* the value lands: the run splits when
the new value reaches an expression slot Postgres resolves at DDL time.
That is knowable from the declarations and from nowhere else — one more
reason the split belongs to the generator rather than to anything
reading the emitted file.

Ten surfaces were driven; eight fail, and the two that pass are both
function bodies. That exception is structural rather than incidental:
`language` is typed as the literal `"plpgsql"`, so the one function form
whose body *is* parsed at creation is a form hejbro cannot express —
not merely one it happens not to emit. The behaviour also survives the
setting that would plausibly change it: a body referencing the new value
applies with `check_function_bodies` both on (the default) and off,
because plpgsql's creation-time check reads syntax and does not resolve
the SQL inside.

**The trigger is computed, not enumerated.** The specs do carry a list
of expression-bearing slots, and the measurements cover all six of them
— but that sentence was written to scope a different rule, and the proof
that it is not an inventory is that a view body is missing from it and
fails. A split condition built on a list inherits every slot nobody
thought of. The generator already holds the expression nodes it is about
to emit, so the question it answers is mechanical: does a value added by
this run appear in any expression node this run emits, outside a
function body? No list, and nothing to keep in sync with the next kind
someone adds.

The failure is also stable across majors: the `55P04` error is
byte-identical on the floor and on 17 — same message, code, severity,
position and routine — so the diagnostic that translates it does not
have to be version-aware.

Finally, `create type … as enum` followed by a use of its values *in the
same transaction* is safe on both majors. A first migration and a
`baseline` therefore never split; only `alter type … add value` can
trigger it.

**Nothing stops it, and the built CLI was run to prove it rather than
read.** A user editing one declaration file — adding a value and a
column that defaults to it — gets `wrote migrations/0002_alter_mood.sql`,
**exit 0, no warning**, and `hejbro verify` then passes all five checks.
The file's two statements are byte-identical to what the engine produces
directly, and its banner hashes match the ones computed independently
through the core API — two paths arriving at the same bytes. Applied
with the tool this project uses today it succeeds; applied in a
transaction it dies. So a migration can pass every offline check hejbro
has and fail only at apply time.

The reasons it is not stopped are all structural: one `generate` run
writes exactly one file and nothing splits a run; the ordering is a
declared kind rank the code's own comment calls structural "rather than
the incidental by-product it was before"; the declaration type-checks
because the enum's column builder carries the freshly added value in its
type; and the CLI adds no validation of its own — validators come from
presets only, and none of the three shipped presets inspects enums. The
example projects declare no enum at all, which is a coverage gap rather
than a guard.

**The fix is in the generator, not in the engine: a run splits at the
transaction boundary.** When a run adds an enum value and something in
the same run references it, the enum statement goes to a preceding
migration file and the rest follows in the next. Three things decided
this over the alternative of marking the file and applying it unwrapped:

- Marking gives back the property this design just bought. "The one
  place we tolerate partial application" is a sentence that should stop
  a design, not qualify it. Every file is wrapped, every ledger row is
  atomic with its file, and the engine has **no special case at all**.
- An unwrapped file would not even reproduce the old semantics. A
  multi-statement string with no parameters is wrapped by the server
  anyway, so genuinely applying statement-at-a-time means finding
  statement boundaries — the banner line is not one line, it is the
  boundary machinery arriving through a side door.
- The generator knows at emit time, from the declarations. That is the
  same direction everything else in this project runs, and the failing
  file measured above is the red test: it is not a fixture anyone had to
  invent.

The cost is stated rather than hidden: **one `generate` run may write
more than one migration.** The rule is narrow — a run splits only where
Postgres's own semantics require a transaction boundary — and it changes
a shipped contract, so it moves the `generate` requirement (below).

Refusing at generation was also weighed and declined: it stops something
that works today, and this project does not build prevention for
platform-inherited failure modes.

A file written before this change can still carry the combination. The
engine cannot fix it, so it explains it: the diagnostic translates
`55P04` into hejbro's own error naming the remedy — regenerate, and the
enum change lands in its own migration.

**Candidates 2–4, and why they are not built:**

- *The generator declares "this file cannot be wrapped"* — **kept, for
  the one case above.** The direct precedent is Atlas's
  `-- atlas:txmode none`, and its real lesson is not the notation but
  the default: absence means *wrapped*. That default is what lets this
  be added without changing the meaning of a single migration already
  written.
- *The generator emits the statement boundaries* — same reservation,
  larger artifact. Worth recording that the generator does join
  statements with a blank line and that every committed example splits
  correctly on it: that is a property of today's renderer, not a
  contract, and relying on it would be reading our own output.
- *Delegate to `psql`* — measured worse, not merely heavier: it gives up
  the atomicity above, cannot put the ledger row in the same
  transaction, and still needs a driver connection to write it.

**The precedent for statement-level resolution stands on an asset this
project gave up.** Atlas records `Applied`, `Total` and `ErrorStmt` and
resumes with `stmts[r.Applied:]`, verifying the statements it already
ran against stored per-statement hashes. Every one of those values
presupposes a statement splitter. Having declined to build one, this
change cannot have that resolution — and takes in exchange the default
Atlas itself ships, one transaction per file.

**What the alternatives paid, for the record.** Flyway guesses which
files can be wrapped by reading them, and the guess has its own bug
trail; its escape hatch is reported to be edition-gated, which we did
not verify and therefore do not rely on. golang-migrate does not wrap by
default, and pays for it with a `dirty` flag that says "broken" without
saying how far it got, recoverable only by a human editing the schema
and forcing a version. drizzle-kit avoids the question by having its
generator plant `--> statement-breakpoint` markers. Postgres-only is what
lets this change skip all three: the database rolls the failed migration
back, ledger row included, so there is no half-state to name.

### DC — The ledger's shape and place

Schema and table name, columns, and whether a row carries the migration's
chain hash. Carrying it makes a file altered after it was applied
detectable against the database — a comparison between two things hejbro
wrote, not an inspection of the schema.

### DD — Concurrency

Two CI runners applying at once is the ordinary case, not the exotic one.
An advisory lock is the genre's answer — Atlas takes one and says so —
and **the choice between the two kinds of lock is a trap that passes in
tests and fails in production.**

Measured: four *sequential* `execute()` calls all landed on the same
backend, so a session-scoped `pg_advisory_lock` taken through
`execute()` appears to be held across calls. Four *concurrent* ones
landed on four different backends, and a session lock taken on one of
them stayed held by a connection the following calls did not get. The
same connection reuse that makes the test green is a property of an idle
pool, not of the contract.

A transaction-scoped lock has no such gap: taken inside `transaction()`
it was observed held during the callback and released the moment the
callback returned, and two `execute()` calls inside one `transaction()`
callback were measured on the same backend. So the lock is
`pg_advisory_xact_lock`, taken inside the same transaction that applies
the file, and **the driver contract is not touched at all.**

The specification's own sentence is the precedent rather than an
obstacle: "pinning a connection any other way means a transaction"
(`cli-commands:236-238`). This change pins a connection by opening a
transaction, which is the way that sentence endorses.

### DE — `reset`'s refusal contract

`check` reports objects the declarations do not manage as inventory, on
the stated grounds that "a project may legitimately leave objects
unmanaged". A `reset` that dropped them would destroy what this tool has
said in its own specification that it does not own. That contradiction is
promoted to a constraint: **reset destroys only what hejbro manages.**
What remains for `[design]` is its behaviour in the presence of the
unmanaged inventory — refuse, require a flag, or report and proceed —
and the confirmation it demands. `generate` already has the idiom for
confirming a destructive change by the dropped object's name.

### DF — Exit codes, command naming, and error codes

`check` set the precedent that three answers are distinguishable: agreed,
disagreed, could not answer. An apply engine's third answer is not the
same as a checker's, and the mapping is contract, not convenience. A
lock held by another runner is a candidate for an answer of its own.

Two constraints on the naming, both measured rather than preferred:

- **`history` is taken, and it means something else.** `hejbro history`
  ships today and is git-derived: `packages/cli/src/history-state.ts:27`
  types its states as `"ok" | "lost" | "rewritten" | "uncommitted"` —
  reachability from a commit, not application to a database. A ledger
  command called `history` would collide with a shipped command's
  meaning.
- **The reusable connection module's error codes are spelled
  `check-`.** `packages/cli/src/check/driver.ts` is already
  command-neutral in behaviour — `--url`, then `DATABASE_URL`, then a
  coded refusal; a dynamically imported driver; a `select 1` probe that
  separates "could not reach" from "could not read" by construction —
  but its codes are `check-connection-missing`,
  `check-driver-missing`, `check-connection-failed`. Reused as-is,
  `hejbro migrate` answers with `error[check-connection-missing]`.
  Whether to neutralize the shared codes or mint per-command ones is
  part of this fork.

## Specification impact

The premise sweep was run as two independent inventories (planner and
researcher) and reconciled; the union is the list below. Notably,
**`openspec/specs/` never states D12's premise — it only leans on it.**
The premise is written down in `docs/specs/2026-08-19-hejbro-design.md`
alone (`:68`, `:214`, `:533`), which means there are few verbatim claims
to retract and several arguments to repair.

### MODIFIED — `migration-format`

- `:15-19` names the banner's baseline marker as having "only" one
  consumer, "a tool deciding whether to run the migration or register it
  as applied", and rests the case for *public* parsers on that consumer
  being someone else. hejbro becomes that consumer.
- `:22-25` carries the same paragraph's conclusion — a false "absent"
  "tells an apply tool to *run* a migration that must only be
  registered". The replacement span is `15-25`, not `15-19`: cutting at
  the first sentence leaves the conclusion of a retracted premise
  standing. (The rule this follows: a replacement span ends where the
  argument ends, not where the paragraph does.)
- 4 scenarios are re-stated with the requirement (`:27, :33, :39, :45`).

If DB settles on option 2, this capability also gains an ADDED
requirement for the banner line that declares a file cannot be wrapped —
including what its absence means.

### MODIFIED — `cli-commands`, `A database hejbro did not create can be adopted`

`:48-51` requires the report to state the registration step "before the
user has a chance to run the file". True, and now half a contract: the
first thing that might wrongly run a baseline is no longer a user, it is
`hejbro migrate`. The human warning stays; the machine half — the engine
registers a baseline rather than running it — is added. 7 scenarios
re-stated (`:57, :64, :69, :75, :82, :88, :93`), one of which
(`:57-62`) carries the premise in its own bytes.

The requirement is not the only place this premise is written down. The
report the command actually prints says: "Next: register … as APPLIED
**in your apply tool** without running it, then confirm your
declarations really match the live schema (a two-path pg_dump comparison
is the check hejbro's own examples use)." Three things follow. The apply
tool it names becomes `hejbro migrate`, so fixing the requirement and
leaving the string would put the spec and the output at odds. "Without
running it" is the engine's contract, already exposed to users. And the
`pg_dump` advice predates `hejbro check`, which ships — stale before
this change and left contradictory by it. All three are repaired here.
Filing the third separately would mean opening an issue to change one
sentence in a function this change is already editing, in a requirement
this change is already modifying: coordination bought at the price of
the thing it coordinates. The function's own doc comment carries nearly
the same sentences as the requirement, so the sweep covers the
implementation comment too, not only the spec.

### MODIFIED — `cli-commands`, `The database driver is an optional dependency`

`:387-390` makes the driver optional on the grounds that "every other
command works without one". **This is the only sentence in the shipped
specs that this change makes false**, and it is false the moment
`migrate` ships. The requirement's title stays true — the driver is
still optional — and its reason is what has to change. 1 scenario
(`:413`).

### MODIFIED — `cli-commands`, `Migrations are generated deterministically from declarations`

`:418-431` says `generate` "writes exactly two artifacts: the next
migration file (carrying only what changed) and the updated snapshot".
The split above makes that false for one narrow case, so the requirement
gains the rule and its boundary: a run writes one migration, and more
than one only where Postgres's own semantics require a transaction
boundary between the statements it produced. Determinism is unaffected
and stays as written — the same declarations against the same snapshot
still produce byte-identical files, and now a byte-identical *number* of
them. 3 scenarios re-stated (`:433, :439, :445`).

**The consequence that looked expensive is cheap, and it was measured
end to end rather than argued.** A migration's banner carries a
parent-snapshot hash and a snapshot hash, so the first of two files ends
at an *intermediate* state — enum changed, table not yet — whose
snapshot must be hashed even though only one snapshot file is ever
committed. Measured: `verify` never recomputes or looks for an
intermediate snapshot; it checks that each entry's parent hash equals
the immediately preceding entry's own hash, and that the chain's tip
equals the hash of the snapshot on disk. A snapshot is a plain keyed
record, so the intermediate one is the previous snapshot with a single
entry replaced. Driven through: the two banners chain, the chain walk
accepts them, the tip matches the committed snapshot, **the final
snapshot's bytes are identical to the unsplit run's**, and both files
apply in order on two Postgres majors.

What remains is seating it in the CLI, and that code holds two traps
worth naming now.

**File naming.** Two of the three prefix strategies derive the version
from the clock alone, at one-second resolution, so a second file cannot
be separated by counting — measured on all three: giving the second file
`count + 1` fixes the index strategy and does nothing for the other two.
`verify` refuses a chain whose migrations share a version, and it does
more than fail: chain linearity and the tip-to-snapshot check are
**skipped**, so a botched split disables the very checks that would
describe it. With `--name` it gets quieter still — measured, the two
files then share their slug as well as their prefix, so the *paths* are
one string. What follows from that (the second write replacing the
first, leaving `verify` nothing to object to) is deduced from what
`writeFileSync` does, not observed: there is no split yet to watch doing
it. The requirement does not rest on the deduction — version separation
is required either way — and the group that builds the split opens with
the test that turns it into an observation.

**What `history` says about the pair.** The first file's banner names an
intermediate snapshot that is never written to disk, and `history`
classifies a migration whose banner hash matches no committed snapshot
as `lost`. The existing machinery absorbs this gracefully — the two
files are a co-add group, the second is the survivor, and `restore`
already points there — but `lost` is documented as the trace of an
accident, "a squash merge (or similar history-flattening) folded its
intermediate declaration state into a later migration's own commit".
This change would make that word appear on a healthy chain produced by
an ordinary `generate`. Nothing crashes; a shipped diagnostic changes
meaning, and that is settled deliberately rather than absorbed.

  *Consequence*: the deferred ledger comparison is a scope decision, not
  a boundary question.

A third entry, because this change is the first to need one and the

- `D⟨next⟩` → **The supported Postgres floor is the lowest still-current
  major that hejbro's own output actually requires — a policy, not a
  fixed number. Today that is 15**, because the emitter writes
  `security_invoker` on views, which arrived in 15. The policy is
  phrased that way so a finding like that one is an *input* to the floor
  rather than a violation of it. *Alternatives*: naming 14, the lowest
  major still under upstream support — rejected because the shipped
  output already falsifies it: the example chain fails on its first file
  with `22023 unrecognized parameter "security_invoker"`, and 14 reaches
  end of life within two months. Holding 14 would have meant either
  gating the emitted parameter behind a declared target version — a
  permanent public knob bought for a two-month window — or dropping
  `security_invoker`, which is a deliberate security default that keeps
  views checked against the invoker's privileges, and giving it up to
  widen a floor is the wrong trade. Also considered: naming no floor
  (D100's stated intent,
  "avoiding any new minimum-Postgres commitment") — its cost is now
  known, because an apply engine that must be correct on PostgreSQL 11
  has to isolate statements a transaction block refuses, which drags in
  a statement splitter, a ledger that records how far an isolated run
  got, and a recovery path for a half-applied file.
  *Consequence, and it is an obligation rather than a note*: **the floor
  that is declared is the floor that is tested.** A minimum nobody runs
  against would reproduce, on the version axis, exactly the gap this
  change exists to close — a claim true of the repository and merely
  presumed of the world. The apply witnesses therefore run on the
  declared floor as well as on 17. *Recorded separately*: the engine's
  own design constraint is ≥ 12, where `alter type … add value` first
  became legal inside a transaction block. Older versions may happen to
  work; they are untested and unsupported. Keeping the policy and the
  constraint apart means a future move of the policy does not disturb
  the reasoning underneath it.

## Measurement protocol

- **A partial failure is produced on purpose, not waited for.** Every
  claim in the partial-failure contract is unobservable otherwise. The
  fixture is a migration whose second statement fails against a real
  server, and the assertions are on what the ledger holds afterwards and
  what the report tells the user to run next.
- **`verify --fix` is run against a split pair before the split ships.**
  It renames files to resolve duplicate versions, and a rename that
  lands between the two halves of one run would break the chain they
  form. Nobody has looked; the guess is that it matters, and a guess in
  this position is exactly what a witness is for.
- **The two silent breakages are witnessed, not assumed.** A file
  carrying its own `commit;` must be observed splitting the atomicity,
  and a parameterized multi-statement call must be observed being
  refused. Both were found by measurement rather than by reasoning, and
  a contract clause whose violation nothing exercises is a sentence.
- **The witnesses run on the declared floor and on 17.** A supported
  version with no witness is a promise about a version nobody ran. This
  also puts a second server image in the harness, which the calibration
  above says is the expensive kind of task, not the cheap kind.
- **The whole example chain runs on the floor, not one file from it.**
  This is not a formality: it is how the floor was found. Applying
  `examples/postgres` on PostgreSQL 14 failed on its first file — a view
  is emitted with `security_invoker`, which arrived in 15 — and the
  eight files behind it were never reached, so that version's verdict on
  them is still unknown. One file passing is not a chain passing, and
  the same unknown now applies to 15 until this witness runs there.
- **Any server error text the diagnostics translate is measured on both
  versions.** The engine turns at least one Postgres error into its own
  coded advice, and error wording is not a constant across majors — this
  repository already carries a scar from `pg_get_viewdef` changing
  between 15 and 16.
- **A whole chain is applied, not one file.** The measurement that
  settled the design put a single migration through the driver; "one
  file passes" and "the committed chain passes" are different claims,
  and the second is the one users depend on.
- **A statement that cannot run in a transaction block is in the
  fixtures**, not merely in the prose.
- **Two runners are raced**, rather than argued about, for whatever DD
  settles on.
- **The one dangerous statement has never been applied to a real
  server.** `alter type … add value` is the only statement this project
  emits that a transaction block could refuse, and it appears in no
  example's declarations and no committed migration — its only
  occurrence outside the emitter is a unit test. Whatever this change
  decides about transactions, the fixture that exercises that decision
  has to be built, not found.
- **Two gates answer narrower questions than their names suggest, and
  this change lands inside both blind spots.** `check-next-marker` walks
  `throwHejbroError`/`hejbroError` call sites only, so a plain
  `throw new Error(...)` in the engine is invisible to it;
  `check:diagnostic-xref` runs one way — every cited code must exist,
  never every code must be cited — so a new `migrate-*` code documented
  nowhere leaves both gates green. The engine's codes are covered by a
  test that fails, not by citing those gates.
- **The live witness asserts counts, not just absence of complaint.** The
  precedent: stubbing a comparison to return nothing left a "reports no
  differences" witness green — fewer comparisons means fewer findings
  means a cleaner report. A witness that never says *how many* it
  applied cannot notice that it applied nothing.
- **Durations are clock-stamped from the first task.** The ledger's
  `actual_min` column holds numbers taken with two different
  instruments: rows whose notes carry an explicit `HH:MM:SSZ-HH:MM:SSZ`
  span come in at 0.54–0.78 of estimate, and rows without one mostly
  above 1.0 (1.68–5.64). One counterexample (a change with no stamps at
  0.50) means the stamp does not *cause* the ratio — but two groups
  measured differently cannot be read as one series, so this change
  stamps its own rows and cites its calibration base as the unstamped
  series it came from.
- Isolated gate runs use `TURBO_FORCE=1`; the turbo cache is shared
  across worktrees.

## Impact

- **Affected code**: in `packages/cli`, a new `src/apply/` holding the
  ledger, the plan, execution, reset and raising a database, plus four
  new command modules and their registration in `src/main.ts`; in
  `packages/core`, the generator-side split (`src/engine/`). Core stays
  pure — the split reads the declarations and the snapshot it is already
  given, adds no filesystem or database access and no runtime
  dependency, so core's own hard gate does not fire. Outside
  `packages/`: the `cli-commands` Purpose, the decision log, three skill
  files, a changeset, the task-time ledger and a `blackbox/` entry.
- **Driver contract**: this engine needs the two capabilities `check`
  deliberately avoided, and `@hejbro/pg` declares both
  (`interactive-transactions`, `session-state` —
  `packages/pg/src/driver.ts:17-20`). Using an existing capability is
  not a spec change, and this engine needs no new one: the lock is
  transaction-scoped, so the contract is untouched. The surface that
  would have changed it — holding a connection without a transaction —
  is not built.
- **One shipped driver cannot run this engine, and the proposal says so
  rather than discovering it later.** `@hejbro/neon`'s HTTP path
  declares `interactive-transactions: false` and its `transaction()`
  always throws; its own comment records that the endpoint runs every
  batch member through the extended query protocol, which takes one
  statement per member — so it can carry neither the transaction nor the
  whole-file send. `migrate` therefore states that it requires the
  interactive-transaction capability, and acquires `@hejbro/pg` by name,
  as `check` already does. Naming the capability matters beyond today's
  drivers: a configurable driver would otherwise be able to plug an
  incapable one in silently.
- **Reused, not rebuilt**: `packages/cli/src/check/driver.ts` already
  resolves a connection string, imports a driver dynamically, and
  separates "could not reach" from "could not read" by construction.
  This change promotes it rather than writing a second one — see DF for
  what its `check-`-prefixed codes cost.
- **Public API**: `@hejbro/core` gains **one** exported entry point — the
  one that generates a run's migrations, however many the run needs.
  That number was first ruled at zero: the split's internals were to
  stay unexported and the CLI was to receive whatever core produced.
  Measurement revised it. `generateMigration`'s result is read directly
  by more than forty files across the preset and driver packages and the
  examples, so changing its shape was not a contained edit; keeping the
  old shape *and* adding an array beside it would have handed a
  split run's first half to every existing caller as if it were the
  whole run. So the old entry point keeps its exact contract for the
  runs it can express, refuses with a coded error the runs it cannot,
  and names the new entry point as what to call instead. One symbol,
  not four, and no caller is silently given half of an answer.
- **Breaking**: none for existing commands. `migrate` is new surface.
- **Changeset**: `minor` — a new capability (D59; the seven published
  packages move together).
- **Skill**: updated in the same PR, per the list above.
- **Decision log**: D12 amended, as drafted above; the ledger-comparison
  boundary recorded as its own entry.
- **`blackbox/`**: this is an owner-driven change and carries its entry
  in the same PR.
