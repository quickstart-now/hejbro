## R3 — Relations renders one line per relation after Relationships, declaration order, always present, collision-omitted, carried tables only

_lead · interpretation · basis R2 · 2026-09-05T22:39Z · ratified: pending_

(P1) One line per relation: `readonly <key>: { readonly target: "<Tables key>"; readonly mode: "one" | "many" };` inside `readonly Relations: { … };`, keys through `renderKey`, targets through `JSON.stringify`. (P2) `Relations` is the last member of a table entry, after `Relationships`: the raw list first, the derived view after it, and nothing is inserted between `Update` and `Relationships` where `sectionBetween` slices -- not because a current assertion would break (the planner corrected that claim: the slice's assertions are all `toContain`), but because widening that slice would let a later `not.toContain` there be silently wrong. (P3) Forward keys in the table's own physical column order, then reverse keys in the emitted `Tables` order (the `computeTables` array); declaration order, as the repository's other emitted artefacts keep it (#740/D4), never alphabetical. Reverse relations need every table, so `Relations` is computed in a second pass over the finished array, keeping the per-table first pass. (P4) Every vendored table carries the member; an empty map renders `readonly Relations: {};` on one line, never omitted. (P5) Omission mirrors `RelationKeysOf`: a key that is both forward and reverse is dropped on both sides; a relation key equal to one of the table's own column keys is dropped; the implementation is "stripId, then omit on collision", never an `endsWith("Id")` test, so a column key of exactly `"Id"` (unreachable through `table()`, reachable through a hand-built export payload -- the emitter's input is external, #740/D4) keeps `"Id"` through `stripId`'s length guard and is omitted by collision rather than emitted as an empty key; the planner adds that hand-built row to the 1.1 table as the one input that separates the two implementations. (P6) `target` is a member of the emitted `Tables` set only: a foreign key onto a table the contract does not carry yields no relation, because the type layer never checks schema-map membership (measured: `RelationKeysOf` accepts `"author"` toward an absent table) and an emitted `target` that names no `Tables` key would leave the consumer's `Database` uncompilable -- the emitter is the only place that can hold this line. `Relationships` is unchanged. Out of scope, recorded: two forward keys on one table stripping to the same relation key (runtime first-wins, type layer mapped-type rule) has no witness and no spec sentence; not in this piece's table. tasks.md: 1.3 splits into 1.3 (the two-repository witness) and 1.4 (references, prelude, guide, changeset) as the planner drafted, Files-edited and Ordering updated accordingly.

## R4 — vendored related chain keeps exactly the declaring chain's stages; offset() after related() exists on neither

_lead · interpretation · basis 653/R2 (owner seal: one query language, the client forwards); packages/query/src/db/chain.ts 738-757 SelectChainRelatedLimited is a bare ChainTerminal (measured in task 1.2: TypeError offset is not a function); #1000 filed for the offset stage · 2026-09-05T23:42Z · ratified: pending_

Task 1.2 stopped on a contradiction between the approved artifacts and the code: the delta, proposal.md and design.md Q4 promised that the vendored client's `.related()` result chain "keeps `.where()`/`.orderBy()`/`.limit()`/`.offset()`", while the declaring side's own related chain (`packages/query/src/db/chain.ts` 738–757: `SelectChainRelatedLimited` is a bare `ChainTerminal`) has never had `.offset()`; design Q4's "the same four stages … (`SelectChainRelated` is the same shape)" could not be true on both halves.

Ruling: the shape wins. The vendored client forwards the declaring repository's chain and offers no stage the declaring chain lacks (owner seal: one query language). The delta sentence is narrowed to "exactly the stages the declaring side's own related chain has — `.where()`, `.orderBy()`, `.limit()` — and no others: the client offers no stage the declaring repository's chain lacks, and `.offset()` after `related()` exists on neither"; design Q4, proposal.md and tasks.md 1.2 are aligned to three stages with the measurement noted. Adding `.offset()` to the related chain is a `query-layer` capability change, not `schema-vendoring`, and is filed as #1000 under #995.
